## 1. 프로젝트 개요

### 1.1 목표

월 500회차 규모의 대체역사 웹소설 및 맞춤형 주문제작 외전 자동화 생산.

### 1.2 편당 정의

- 1회차 = 약 5000자
- 월 500회차 = 일 평균 17회차
- GPU 생산 용량은 충분. **실질 병목은 사람의 검수 시간.**

### 1.3 하드웨어

- 서버: 물리 서버 GL10
- CPU: Intel 12코어
- RAM: **64GB** (증설 불가)
- VRAM: **48GB** (A40)

### 1.4 운영 규모

- 동시 연재 관리 작품: 최대 2개
- 동시 활성(메모리 상주) 작품 인스턴스: 1개

## 2. 핵심 설계 철학

- **전략과 전술의 분리**. 거시 개연성과 미시 일관성을 다른 도구로 본다.
- **시간 분해**. 기획 주기는 1~2일의 콜드 스타트를 감당하고, 생성 주기는 회차당 수 분의 실시간 판정을 요구한다.
- **RAM을 통한 모드 분리**. 하드웨어 제약이 아키텍처의 경계선을 그어준다.
- **모델 계열 통일**. Qwen 계열(집필·임베딩·리랭커)로 맞춰 토크나이저·지시어 규약을 공유한다.
- **2단계 판정**. Qwen 초벌 → Claude 정밀 재판정 → 수동 큐레이션.
- **인간의 자리**. 최종 검수·커밋·앵커 확정에 사람이 개입. AI는 생성과 1차 판정.

**한 문장 요약**: 사람이 검수·커밋하는 반자동 웹소설 생산 파이프라인. 기획단에서 거시 앵커를 풀 역사 그래프로 검증하고 락을 건 뒤, 생성단에서 시대별 그래프로 회차 단위 개변을 실시간 판정한다.

## 3. 아키텍처 개요

### 3.1 4계층 데이터 구조

| 계층 | 인스턴스 | 가동 시점 | 역할 |
|---|---|---|---|
| 원본 RDB | Original PostgreSQL | 상시 | 정사 연표·인물·사건, 임베딩 캐시 |
| 전략 그래프 | 풀 Original HelixDB | 역설계 세션 시에만 | 기획단 앵커 설계, 대형 개연성 검증 |
| 작품 RDB | 작품 PostgreSQL (스키마 novel_XXX) | 상시 | 작품 SOT, 앵커 경로, 판정 결과 |
| 전술 그래프 | 시대별 통합 HelixDB | 회차 생성 세션 시 | 회차 판정, 원역사 대조, 작품 내 일관성 |

### 3.2 PostgreSQL 스키마 구성

```
스키마 original     (상시, pipeline_user는 SELECT만)
스키마 novel_XXX    (작품별, pipeline_user는 ALL)
스키마 meta         (era_profiles, novels, anchor_paths 등)
```

### 3.3 전략/전술 이원화

**전략 레이어 (기획단)**
- 작품 시작 시, 대형 전환점마다 수행
- 거시 앵커(최종 목적 상태)와 중간 징검다리 사건 설계
- 풀 Original HelixDB를 통한 개연성 검증
- 산출물: 앵커 경로, 개연성 근거, 중간 가이드라인
- 실행: 사람(작가) + Claude

**전술 레이어 (생성단)**
- 회차마다 수행
- 앵커 경로 안에서 씬·사건·인물 작성
- 시대별 통합 HelixDB를 통한 실시간 일관성 판정
- 산출물: 회차 본문, 씬 메타데이터, 판정 결과 SOT
- 실행: Qwen-35B + Claude(판정) + 사람(검수)

### 3.4 앵커 락 + 가이드라인 이원화

- **대형 앵커**: 락(Lock). 확정 후 전술 레이어에서 불변.
- **중간 징검다리**: 가이드라인. 기본 준수하되 자연스러운 흐름이 발견되면 무시 가능.
- 가이드라인 무시 시 판정 근거가 작품 DB에 기록되어 추후 기획단 재검토의 입력이 됨.

### 3.5 provenance 태깅

시대별 HelixDB는 원역사 노드와 작품역사 노드를 공존시키되 `provenance` 속성으로 구분.

- `original_baseline`: 원역사 베이스라인 (읽기 전용)
- `novel_generated`: 작품 내 생성된 변형·신규 사건

쓰기 경로는 `novel_generated`만 허용하도록 강제.

### 3.6 리트리벌 파이프라인

3단계로 확정:

```
쿼리 → 임베딩(Qwen3-Embedding)
    → HelixDB 벡터 검색 (top-K)
    → 리랭커(Qwen3-Reranker)로 재순위 (top-N)
    → PostgreSQL에서 본문 Fetch
    → Claude 판정 입력
```

## 4. 운영 모드

배타적으로 동작하는 5개 모드(모드 0·0b 추가).

| 모드 | 명칭 | 가동 | 중지 | 빈도 |
|---|---|---|---|---|
| 0 | 원본 구축 | PostgreSQL(쓰기), Qwen-35B, 임베딩 | 양쪽 HelixDB | 프로젝트 초기 1회. 수 주~수 개월. |
| 0b | 시대 단위 Claude 재판정 | PostgreSQL(쓰기), Claude API | Qwen-35B, 양쪽 HelixDB | 작품 기획 진입 시. 시대당 수 시간. |
| 1 | 역설계 (전략) | PostgreSQL, 풀 Original HelixDB, Claude, 임베딩·리랭커 | Qwen-35B, 시대별 HelixDB | 작품당 수 회~수십 회 |
| 2 | 회차 생성 (전술) | PostgreSQL, 시대별 HelixDB, Qwen-35B, Claude, 임베딩·리랭커 | 풀 Original HelixDB | 회차마다. 일 10~20회. |
| 3 | 휴지 | PostgreSQL만 | 나머지 전부 | 기본 상태 |

모드 전환은 사람이 선언, 하네스가 프로세스 기동/중지를 자동화.

**모드 0·0b 신설 배경**: Original RDB 구축 시 Qwen-35B 초벌 판정을 돌리는 단계(0)와, 작품 기획 시 해당 시대 부분집합을 Claude로 재판정하는 단계(0b)를 모드 1·2와 별도로 분리. 상세는 [Original RDB 스키마 설계서](./original_rdb_schema_v1.md) §5 참조.

## 5. 모델 스택

### 5.1 집필 모델

Qwen-35B, 4bit 양자화. VRAM 35~40GB. 모드 2에서 사용.

### 5.2 원본 구축·초벌 판정 모델

Qwen-35B (집필과 동일 모델 재사용). 모드 0에서 사용.
- 엔티티·관계 추출
- 사건 추출
- 파급력·범위 초벌 판정
- fidelity_score 부여

### 5.3 임베딩 모델

Qwen3-Embedding 계열. 잠정 기본선: Qwen3-Embedding-4B + MRL 1024차원.

| 크기 | 출력 차원 | VRAM(fp16) | 1000만 청크 Int8 SQ 벡터 RAM |
|---|---|---|---|
| 0.6B | 1024 | 1~2GB | 약 10GB |
| 4B | 2560 | 8GB 내외 | 약 25GB |
| 8B | 4096 | 16GB 내외 | 약 41GB |

문체 비교는 위 의미 임베딩과 별도 역할로 [Munche v1/v2 검증 계획](./plans/20260914-munche-style-embedding-integration-plan-v0-1.md)에 편입한다. 먼저 원문 선별·학습 전후 평가에 적용하고, 이후 예문 검색을 검토한다. 역사 검색과 정사 판정은 대체하지 않는다.

### 5.4 리랭크 모델

Qwen3-Reranker 계열. 잠정 기본선: Qwen3-Reranker-0.6B.

### 5.5 판정·재판정 LLM

Claude (외부 API).
- 모드 0b: Original RDB의 시대 단위 재판정
- 모드 1: 전략 레이어 앵커 판정
- 모드 2: 전술 레이어 회차 판정

### 7.2 우선순위 높음 (구축 전 결정 필요)

- **임베딩·리랭커 모델 크기 최종 확정**
  - Qwen3-Embedding: 0.6B / 4B
  - Qwen3-Reranker: 0.6B / 4B
  - MRL 저장 차원 (1024 / 2048 / 2560 / 4096)
  - 파일럿 실측 필요

- **모드 2 VRAM 배치 전략**
  - Qwen-35B(4bit) + 임베딩 + 리랭커 48GB 공존 방식
  - A. 임베딩·리랭커 CPU int8
  - B. 둘 다 GPU 잔여 VRAM
  - C. 임베딩만 GPU, 리랭커는 CPU

- **시대 프로파일 초기 목록**
  - era_tags의 실제 값 집합
  - 작품별 적용 매핑
  - meta.era_profiles 테이블 세부

- **역사 카테고리 필터의 언어별 매핑**
  - 4개 언어 각각의 "역사 카테고리" 실제 경로

- 그래프 엣지 데이터의 출처 (자동 NER+관계 추출 vs 수동 큐레이션 비율)
- 엣지 추출 파이프라인 품질 기준
- entity_subtype 표준 어휘 정립

### 7.6 파일럿 실측 필요 항목

**Qwen3 모델 스택**
- 크기별 실제 VRAM 점유
- 모드 2 3자 공존 시 OOM 임계
- MRL 저차원 절단 시 품질 저하
- 한·중·일·영 교차언어 검색 품질

**풀 Original HelixDB**
- 콜드 스타트 시간 (1~2일 내)
- 실제 RAM 피크 (50GB 이하)
- 서브그래프 export 기능
- 한국어 단일 언어 선행 구축

**시대별 통합 HelixDB**
- 구축 시간
- provenance 필터 쿼리 응답 속도
- novel_generated 누적에 따른 성능 변화

**Original 구축 파이프라인 (v3 신규)**
- 청크당 Qwen-35B 처리 시간
- 전체 구축 기간 추정
- Qwen 판정 품질 샘플 검증 (Claude 재판정과의 일치도)
- Claude 재판정 비용 추정 (시대당)

**Qwen-35B 공존**
- 시대별 HelixDB 동시 가동 시 RAM 경합
- 페이지 캐시 경합 지연

**기타**
- HelixDB 중지→재기동→인메모리 적재 시간
- 위키 덤프 시대 태그 자동화 품질
- 언어별 카테고리 매핑 일관성

## 10. 버전 이력

- **v1**: 3계층 DB 구조, 단일 HelixDB 인스턴스 전제.
- **v2**: 4계층 DB 구조, 전략/전술 분리, 운영 모드 3종, provenance 태깅, 앵커 락+가이드 이원화, 씬 메타 자동화 방침 확정.

- **v3 (이 문서)**: **인덱스 문서로 역할 전환 시작**. Original RDB 스키마 별도 문서로 분리(original_rdb_schema_v1.md). 모드 0·0b 신설. 2단계 판정 파이프라인 확정. 하위 문서 인덱스 섹션(§6) 신설. 미결 사항 통합 추적 체계(§7) 재구성.
