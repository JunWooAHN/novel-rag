- 작성일: 2026-09-14
- 상태: 전체 계획에 편입. 모델 실행·품질 검증·코드 구현은 미실시.
- 상위 기준: [핵심 시스템 설계](../systems/README.md). 상세 계약: [통합 아키텍처 v5](../20260914-novel-factory-architecture-v5.md). 이 문서는 문체 encoder 검증과 S0~S3 구현 순서를 상세화한다.
- 적용 범위: 문체 데이터 준비, 학습 전후 평가, 후속 집필 보조. 역사·정사 모델과 생성 모델의 책임은 유지한다.
- 연결 문서: [toy-tune 실행·아키텍처 계획](20260914-toy-tune-architecture-and-backendai-bootstrap-plan-v0-1.md), [SQLite 역사·정사 논의](../reports/20260908-alternate-history-sqlite-canon-report-v0-1.md)

## 1. 결정과 모델 후보

사용자 정정에 따라 Munche는 소설 원문·생성문의 문체 임베딩 전용으로 사용한다. 기준 모델은 `Baragi-AI/Munche-768`이며 `Baragi-AI/Munche-v2-768`은 같은 원문으로 비교 후 선택한다. 역사·과학·인물 자료의 의미 검색은 별도 Granite 경로다. 이전의 모든 임베딩 Munche 통일·역사 검색 보조 제안은 폐기한다. 본문 생성 Gemma, 기획·검수·추출 SOTA, SOTA 본문은 품질 비교용이라는 정책은 유지한다.

Munche-768은 한국어 소설 문체용 768차원 임베딩이며, `google/embeddinggemma-300m`에 붙이는 LoRA adapter다. 문단·문장부호를 보존하고, 내용·장르와 문체가 완전히 분리된다고 가정하지 않는다. 생성용 Gemma 31B의 학습 adapter와는 다른 모델이다. [v1 모델 카드](https://huggingface.co/Baragi-AI/Munche-768)

v2 역시 768차원이다. 카드의 권장 처리는 문서 prefix, 1024-token window/512-token stride, 겹침 보정 pooling이다. BF16으로 학습·평가했으며 FP16 activation은 지원하지 않는다고 명시한다. 이전 평가의 학습 노출 문제로 평가 표본을 다시 구성했다는 설명도 있으므로, v1 카드와 v2 카드의 숫자를 직접 비교하지 않는다. 보고된 성능은 제작자 보고이며 우리 원문의 검증을 대신하지 않는다. [v2 모델 카드](https://huggingface.co/Baragi-AI/Munche-v2-768)

모델 다운로드 전 base 접근 권한과 이용 조건을 확인한다. 모델 사용 권한이 우리 학습 원문의 이용 권한을 대신하지 않는다.

## 2. 전체 시스템에서의 역할

아래는 우리 프로젝트의 설계 결정이다. Munche 자체에 이 전체 기능이 구현되어 있다는 뜻은 아니다.

| 구성 요소 | 담당 | 담당하지 않는 것 |
|---|---|---|
| 원역사·작품별 공개 정사 | 무엇이 언제 사실인지, 인물에게 알려진 정보인지 판정 | 문체 점수로 사실 여부 결정 |
| 구조화·키워드 검색 | 장면에 필요한 역사·설정 근거 조회 | 문체 유사도 판정 |
| Granite 의미 임베딩 | 영어 우선 역사·과학·인물 자료의 내용 검색 | 소설 문체 평가 대체, 사실성의 자동 확정 |
| Munche 문체 임베딩 | 소설 원문·생성문의 문체 비교, 문체 분포 점검·예문 검색 | 역사·과학·인물 자료 인코딩, 문장 생성, 정사 갱신 |
| 생성용 Gemma + 웹소설 LoRA | 지시·근거·문체 조건을 받아 본문 작성 | 임베딩 벡터를 그대로 읽거나 정사를 자동 확정 |
| SOTA 역할 모델 | 기획·검수·추출과 Gemma 생성물의 비교 기준선 | 운영 본문 writer 대체, 비교 출력의 학습 정답 자동 편입 |

문체와 지식 검색은 모델·index·평가를 분리한다. Munche의 역사 검색 실험은 이 계획에서 제외한다. 지식 검색은 [영어 위키백과·Granite 계획](20260914-enwiki-granite-knowledge-ingestion-plan-v0-1.md)을 따르며 Granite 97M/384차원과 311M/256차원을 비교한다. 한쪽 encoder 장애를 다른 쪽 모델로 대체하지 않는다.

기존의 ‘공용 오리진 + 작품별 한 개의 공개 역사 + 집필 중 임시 분기’는 바꾸지 않는다. 문체 자료는 역사전표가 아니며 공개 정사에 병합하지 않는다.

후속 집필에서는 두 입력을 구분한다.

- 사실 패킷: 정사 revision·시점·인물 지식으로 검증된 근거.
- 문체 패킷: 목표 문체를 보여주는 짧은 참고 예문과 출처. 예문의 인물·사건은 해당 작품의 사실로 가져오지 않는다.

Munche의 벡터는 검색·비교에 사용하고, 생성 모델에는 선택된 예문을 텍스트로 제공한다. 두 모델의 가중치를 병합하지 않는다. 문체 점수가 높더라도 정사 위반을 상쇄할 수 없다.

## 3. 먼저 할 작은 실험

첫 LoRA 저장·재로드 연습을 문체 DB 완성 때문에 지연시키지 않는다. 기존 toy-tune C/D 단계 옆에 별도 오프라인 실험으로 둔다.

1. 사용자가 지정하고 이용 가능한 원문에서 30~60개 구간을 고른다. 대화·서술·액션 등 장면 유형을 표시하고, train/validation/test를 먼저 분리한다.
2. v1과 v2를 각각 동결해 같은 구간을 임베딩한다. base EmbeddingGemma는 Munche 로딩 의존성으로만 두고 별도 운영 encoder로 추가하지 않는다. 모델별 입력 처리를 기록한다.
3. 이름만 바꾼 구간, 내용은 비슷하나 문체가 다른 구간, 내용이 달라도 목표 문체에 가까운 구간을 사람이 확인한다. 변형본은 같은 split에 묶는다.
4. 첫 생성 실험에서 동일한 평가 프롬프트·길이 조건으로 Gemma 학습 전후 결과를 모으고, 선택한 시점에 SOTA의 독립 생성물을 비교군으로 추가한다. 문체 순위와 블라인드 사람 평가를 대조한다. 비교 입력·버전·비용·누수 통제는 상위 아키텍처 §11.5를 따른다.
5. 순위가 사람이 느끼는 문체 차이를 유용하게 반영할 때 평가 보조로 채택한다. 부합하지 않으면 데이터 탐색용으로 제한하거나 보류한다.

산출물은 모델·전처리 manifest, 구간별 벡터, 비교 결과, 사람이 검토한 채택 판단이다. 처음부터 별도 DB나 UI를 만들지 않는다.

## 4. 데이터 준비와 평가 규칙

- 원문이 정답이라는 기존 원칙을 유지한다. 역질문·개요 추출은 SOTA가 담당하며 Munche는 원문을 재작성하지 않는다. SOTA 비교 생성물도 원문 정답에 자동 편입하지 않는다.
- 문체 분포를 보고 대표 구간과 드문 구간을 함께 확보한다. 낮은 유사도를 이유로 좋은 장면을 자동 삭제하지 않는다. 작가 문체를 단일 평균 벡터 하나로만 정의하지 않는다.
- split은 임베딩·대표 구간 선정 전에 고정한다. 같은 원문 범위와 겹치는 window·변형본은 split을 넘지 않는다. 중복·유사 복제는 별도 텍스트 검사로 확인한다.
- 목표 작가의 문체 학습 평가는 해당 작가 내 시간순·회차 단위 분리가 가능하다. 다른 작가로의 일반화를 측정할 때만 별도의 작가 단위 holdout을 설계한다.
- 학습 및 예문 검색용 문체 reference bank는 train에서만 만든다. validation은 개발 평가, test는 최종 평가로 분리하며 평가 정답을 예문 검색에 노출하지 않는다.
- 줄바꿈·문단·문장부호를 임의 통일하지 않는다. tokenizer 기준 길이, prefix와 특수 토큰 예산을 검사하고 초과 입력을 조용히 자르지 않는다.
- 장면 유형·시점·길이를 맞춰 비교하고, 평균 하나보다 구간별 점수와 분포를 함께 본다. cosine 0.8을 ‘문체 재현율 80%’로 해석하지 않는다. 임계값은 실험 전에 임의 확정하지 않는다.
- 문체 유사도 외에 정사 준수, 지시 준수, 반복, 원문 복제, 장문 연결성과 사람 선호를 별도로 평가한다.

v2에는 인간 원문과 LLM 재작성본을 구분하는 학습 신호가 포함된다. [학습 방법](https://huggingface.co/Baragi-AI/Munche-v2-768#학습-방법) 따라서 생성문의 좋은 문체와 단순한 인간/AI 구분 신호가 섞일 가능성을 검증해야 한다는 것이 우리의 판단이다. 초기에는 Munche 점수를 직접 학습 loss, 강화학습 reward 또는 유일한 모델 선정 기준으로 사용하지 않는다.

## 5. 저장·재현성과 SQLite/PostgreSQL 경계

초기는 기존 `ArtifactStore`를 통해 파일 기반 벡터 묶음을 보존한다. 검색 필요가 생기면 논리적 `style_store`를 SQLite로 구현한다. 물리적으로 별도 `style.sqlite`를 둘 수 있으나, 파일명이나 DB 제품을 도메인 계약으로 고정하지 않는다.

- 기존 SQLite 벡터 확장 선택과 문체 임베딩 모델 선택은 독립이다. SQLite-vector 기반 문체 검색은 후속 구현 후보이며 현재 구현됐다고 간주하지 않는다.
- 문체 예문은 Munche, 역사·과학·인물 자료는 Granite로 처리하고 별도 공간·collection/index로 관리한다. 두 모델의 벡터·점수를 직접 혼합하지 않는다. Munche v1/v2도 차원이 같다는 이유로 섞어서 검색하지 않는다.
- 저장 항목: source ID/hash, 작품·회차·구간 범위, split, model/base/tokenizer의 고정 revision, 전처리·pooling 버전, dtype, 차원, 정규화 여부, artifact hash.
- float32 768차원은 벡터 하나당 3,072바이트다. 메타데이터·인덱스·원문·DB 여유 공간은 별도다. 작은 실험은 정확 검색부터 시작하고 규모가 커질 때 검색 방식을 측정한다.
- 벡터는 원문과 설정으로 재생성할 수 있는 파생물이다. 비공개 원문과 함께 접근을 제한하고 Git에는 합성 fixture와 검토한 집계만 둔다.
- PostgreSQL로 이동할 때 source ID, 필터, embedding-space 식별, cosine 점수 의미를 유지하는 adapter 계약을 검증한다. 정사 DB와 문체 저장소가 같은 서버에 있어야 할 이유는 없다.

## 6. 클린 아키텍처와 실행 위치

후속 구현 시 `application`에 `StyleEncoder` port를 두고 텍스트 묶음·인코딩 명세를 받아 표준 자료형의 벡터와 계보를 반환하게 한다. 구체 SentenceTransformers/PEFT 로딩은 outbound adapter에 둔다. 도메인에 Torch tensor나 SQL을 노출하지 않는다.

문체 검색이 실제 필요해질 때만 `StyleReferenceReader` port를 추가한다. 파일 산출물에 기존 store를 재사용하며 지금 빈 adapter·폴더를 미리 만들지 않는다. style profile은 생성용 model/engine 설정과 분리하고 선택 기능으로 로드한다.

- H200: 문체 벡터를 먼저 배치 생성하고 encoder를 내려 생성용 모델 학습과 VRAM을 경쟁하지 않게 한다.
- 다른 서버: 고정 원문 묶음·모델 revision·전처리로 재생성하거나 기존 벡터 artifact를 반입한다.
- 맥북: H200에서 만든 벡터와 예문 bank를 소비하는 경로를 먼저 확보한다. 새 텍스트의 임베딩은 실제 지원을 검증한 encoder 실행 환경이 필요하다. MLX로 생성할 수 있다는 사실이 Munche adapter의 MLX 지원을 뜻하지 않는다.
- 모델 카드의 base + adapter + 원래 pooling/projection 경로를 재현한다. CPU/MLX 지원, dtype 및 패키지 조합은 별도 capability 검사 대상으로 두며 FP16으로 자동 대체하지 않는다.

학습 중 운영 DB나 Munche 서비스에 매 step 접속하지 않는다. 데이터 선별 결과·문체 패킷·평가 기준을 snapshot으로 고정한다.

## 7. 단계와 완료 조건

| 단계 | 범위 | 완료 조건 |
|---|---|---|
| S0: 오프라인 검증 | 소량 원문, v1/v2, 내용·문체 대조군 | 모델 로드·차원·정규화·길이 검사, 사람 검토와 한계 기록 |
| S1: toy-tune 평가 | Gemma baseline/LoRA와 선택 SOTA 비교 출력에 동일 문체 평가 적용 | split 누수 없음, 동일 reference·encoder 조건, 사람 평가·별도 품질 지표와 함께 비교 |
| S2: 문체 검색 | SQLite 문체 bank, 텍스트 예문 패킷 | 검색에 test 제외, 사실 패킷과 분리, 예문 원문 복제 점검 |
| S3: 이동·확장 | 필요 시 PostgreSQL, 로컬 encoder, 후보 재정렬 | 저장소·실행 환경 교체 검증, 품질·지연·비용 실측 |

현재 확정은 Munche의 소설 문체 전용 역할과 검증 순서다. 최종 v1/v2 선택, 문체 점수 임계값, DB schema, Mac 실행 방식은 실험 후 결정한다. 모델 설치·원문 업로드·유료 SOTA 호출·학습 실행은 이 문서 수정에 포함하지 않는다.
