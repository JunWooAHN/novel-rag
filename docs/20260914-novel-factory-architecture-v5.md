## 1. 이 문서의 지위와 이전 설계 변경

[핵심 시스템 설계](./systems/README.md)가 전체 시스템의 기준이며 이 문서는 상세 해설이다. 4월 통합 설계 v4.1과 프로젝트 인덱스 v3의 하드웨어·모델·DB 전제는 역사적 기록으로 남긴다. toy-tune 구현 상세와 Munche 실험 절차는 하위 계획을 따른다. 목표 구조와 실제 구현이 다르면 §15의 구현 현황을 먼저 확인한다.

| 이전 전제 | 현재 기준 |
|---|---|
| A40 서버 한 대에 모델·DB 배치 | 할당된 Backend.AI H200을 첫 학습 환경으로 사용. 다른 GPU·맥북·독립 DB 서버로 교체 가능 |
| PostgreSQL + 전략/전술 HelixDB | 온톨로지와 관계형 저장을 중심으로 SQLite 우선. PostgreSQL은 교체 가능한 후속 구현 |
| Qwen 계열로 생성·임베딩 통일 | 생성 Gemma, 소설 문체 Munche, 지식 의미 검색 Granite. 기획·검수·추출과 비교용 생성은 SOTA |
| 여러 역사 분기·상시 그래프 인스턴스 | 공용 원역사 + 작품별 단일 공개 정사. 집필 작업만 일시적으로 분기 |
| 생성 모델이 설정·문체를 모두 기억 | 사실은 근거 패킷, 문체는 원문 학습·참고 예문, 생성은 별도 모델 |
| 고정 생산량·VRAM·복구 시간 추정 | 실제 환경과 원문으로 측정한 뒤 목표 확정 |

유지하는 원칙은 목적론적 역사 설계, 보조 사건의 적극적인 창조, 정방향 영향 검토, 작가 승인, 승인된 역사표의 집필 구속력, 전략/전술 분리, 출처 추적, 원본/파생 데이터 구분, 클린 아키텍처다. 온톨로지는 데이터의 의미 규칙이며 DB 제품 자체를 대체하는 기술이 아니다.

`legacy`의 PostgreSQL/Weaviate, PostgreSQL/HelixDB, Supabase는 서로 다른 시점의 기술 선택이며 동시에 도입할 요구가 아니다. Hermes·Claude도 고정 의존성으로 승계하지 않는다. 오케스트레이션은 application use case, 추론·기획·검수·추출은 역할별 SOTA adapter로 교체한다. `legacy` 원문은 수정하지 않고 설계 의도의 근거로 보존한다.

## 2. 시스템 목적과 비목표

### 목적

1. 작가의 최종 앵커에서 선행 조건·중간 사건을 역산하고, 간극을 메우는 사건을 창조하여 작품의 역사표를 설계한다.
2. 개입과 창조 사건의 정방향 파급효과를 검토하여 원역사·공개 역사·다른 앵커와의 충돌을 드러낸다.
3. 작가가 승인한 역사표를 잠그고 Gemma가 이를 지정 문체의 소설로 구현하게 한다.
4. 원역사, 승인된 미래 역사표, 공개된 작품 사실, 인물의 인지를 구분하고 공개 전표를 단일 이력에 반영한다.
5. 기존 소설에서 역사표·문맥 입력을 역구성하여 문체와 명세 준수를 학습하고 SOTA 생성물과 비교한다.
6. Gemma/Munche/Granite의 역할 분리를 유지하면서 학습 위치, 실행 엔진, DB 제품·위치와 SOTA provider를 독립적으로 바꾼다.

### 현재 비목표

- 위키백과 전체 적재, PostgreSQL, MLX, 문체 검색 UI를 첫 학습 전에 완성하기.
- 무제한 세계선 시뮬레이션, 자동 공개, 다중 사용자 SaaS, 상시 분산 에이전트 군집.
- 문체 점수 하나로 좋은 소설이나 사실성을 판정하기.
- 역사 개변 확률·성공률·개연성 점수로 경로의 채택 여부를 결정하기.
- DB 업데이트 때마다 생성 모델을 다시 학습하기.

## 3. 논리 구성과 소유권

```text
원역사·과학·인물 자료 → 출처 있는 상태·조건·관계 → 원역사 릴리스
                                                   │
작가의 결말 앵커 → SOTA 역설계 → 조건 간극 → 보조 사건 창조
                       ↑                           │
                       └── 수정 ← 정방향 영향 검증 ←┘
                                      ↓
                              작가 승인 → 역사표 잠금
                                      ↓
                       장면 명세 + 사실 패킷 + 문체 예문
                                      ↓
                           Gemma 집필 → 검수·전표 추출
                                      ↓
                           승인·공개 → 단일 공개 정사

선택 소설 원문 → SOTA 입력 역구성 → toy-tune → Gemma 학습·평가
                                              ↑
                                Munche 문체 평가 / SOTA 비교
```

| 책임 영역 | 소유하는 것 | 금지되는 책임 침범 |
|---|---|---|
| 지식 구축 | 자료 원본, 추출·교정 이력, 원역사 릴리스, 온톨로지 | 소설 사건을 실제 역사로 편입 |
| 역사 설계 | 앵커, 조건·간극, 후보 경로, 보조 사건, 영향 보고서, 승인·잠금 | 승인 없는 앵커 변경, 검색 점수를 인과 판정으로 사용 |
| 작품 관리 | 기획 revision, 초안, 공개 본문, 역사전표, 정사 revision | 공유 원역사를 작품 때문에 수정 |
| 문체 자산 | 허용된 원문, 문체 reference bank, 벡터와 전처리 계보 | 문체 예문의 사건을 작품 사실로 사용 |
| toy-tune | 동결 데이터셋, 실험 실행, 학습·생성 평가, 모델 export | 운영 정사 쓰기, 원문 전체 무단 수집·업로드 |
| 운영 도구 | 환경 준비, 접속, 명시적 파일 전송, 백업·복구 | 도메인 규칙을 SSH 스크립트로 우회 |

이들은 논리적 경계다. 영역마다 별도 서비스나 DB 서버를 배포할 필요는 없다. 기존 `webnovel-writer/`는 참고·연동 대상이며, 새 설계의 구현체로 자동 간주하거나 toy-tune에서 내부 모듈을 직접 import하지 않는다.

### 3.1 확정된 모델 역할

| 역할 | 사용할 모델 | 산출물·제약 |
|---|---|---|
| 운영 본문 생성·재작성 | Gemma 계열. 주 목표는 Gemma 4 31B 문체 학습 모델 | 초안·수정 본문. SOTA를 운영 writer로 자동 대체하지 않음 |
| 소설 문체 임베딩 | Munche. `Munche-768` 기준, v2는 비교 후 선택 | 소설 원문·생성문의 문체 비교와 예문 검색 전용. 역사·과학 자료를 인코딩하지 않음 |
| 지식 의미 임베딩 | Granite 97M R2 / 384차원이 첫 기준선. 311M R2 / 256차원과 비교 | 영어 역사·과학·인물 자료의 의미 검색. 대량 인덱싱 전 최종 구성 선택 |
| 기획 | 역할별로 지정한 SOTA 모델 | 앵커·플롯·장면 개요·개연성 검토 |
| 검수 | 역할별로 지정한 SOTA 모델 | 문제 위치·근거·수정 지침. 운영 본문 수정은 Gemma가 수행 |
| 추출·역질문 | 역할별로 지정한 SOTA 모델 | 자료의 사건·관계, 본문의 역사전표 후보, 학습 입력 후보 |
| 비교용 본문 생성 | 선택한 SOTA 모델 | Gemma와 동일 과제의 비교 artifact. 운영 원고·정사·학습 정답에 자동 편입하지 않음 |
| 최종 판단 | 사용자 + 프로그램의 결정적 무결성 검사 | 모델 점수로 공개 승인·정사 트랜잭션을 대체하지 않음 |

SOTA는 영구 모델명이 아니라 실행 시 선택하는 상위 성능 모델 역할이다. `planner`, `reviewer`, `extractor`, `comparison_writer`별 provider/model/version을 지정한다. 같은 SOTA 모델을 여러 역할에 사용할 수 있지만 요청·출력 계약과 기록은 구분한다. 특정 업체나 현재 순위 1위를 이 문서에서 확정하지 않는다.

SOTA 접근 불가·호출 실패 시 해당 단계는 대기/실패로 기록한다. Gemma로 몰래 대체하거나 검수를 생략해 통과시키지 않는다. 결정적 파싱·schema 검사에는 LLM을 호출하지 않는다.

## 4. 클린 아키텍처와 교체 축

### 4.1 의존 방향

`application → domain`, `adapters → application의 ports/domain`을 따른다. `bootstrap`만 구체 구현과 설정을 조립한다. `ops`는 조립된 프로그램의 실행 위치를 정한다.

- domain: 식별자, 사실 상태, 시간, 전표, 패킷, 실험·산출물 의미. SQL·Torch tensor·SSH 객체를 포함하지 않는다.
- 역사 설계 domain: 앵커, 사건의 선행 조건·효과, 간극, 경로, 계획 승인·잠금 규칙. 모델이 작성한 인과 설명을 검증된 물리 법칙으로 취급하지 않는다.
- application: 데이터 준비, 근거 컴파일, 학습·평가, 정사 반영 등 use case와 필요한 port.
- adapters: SQLite/PostgreSQL, 파일, Transformers/PEFT, MLX, encoder, 필요 시 외부 API.
- inbound: 초기 CLI와 수동 파일 입력. UI·스케줄러는 이후 같은 use case를 호출한다.

### 4.2 독립적으로 선택할 항목

| 축 | 초기 경로 | 후속 경로 | 공통 계약 |
|---|---|---|---|
| 실행 호스트 | Backend.AI H200, 로컬 CPU 준비 | 다른 CUDA 서버, 맥북 | job/run 명세, 환경 기록 |
| 생성·학습 엔진 | 검증 후 Transformers/PEFT | 검증 후 MLX 등 | 지원 capability, 모델 참조, 입출력 artifact |
| 지식 저장 | 동결 패킷, 이후 SQLite | 원격 PostgreSQL | revision·시점·인물 지식의 의미 |
| 문체 encoder | Munche v1/v2 비교 | 채택 Munche의 지원 runtime·revision 변경 | 문체 space ID, 벡터·전처리 계보 |
| 지식 encoder | Granite 97M / 384차원 | 311M / 256차원 비교 후 선택, runtime 변경 | 지식 space ID, 검색 품질·차원·전처리 계보 |
| SOTA 역할 모델 | 역할별 provider/model 설정 | 새로운 SOTA 모델·provider | 역할별 입출력, 요청 hash, 버전·비용 기록 |
| 저장 매체 | 파일시스템 | 다른 디스크·객체 저장소 | 불변 ID, checksum, 발행 완료 의미 |

원격 GPU가 로컬 DB에 직접 접속할 필요는 없다. 데이터 준비에서 패킷을 고정해 반입하면 된다. 반대로 독립 PostgreSQL을 사용해도 학습·생성 엔진을 바꾸지 않는다. DB·엔진 교체는 adapter와 계약 테스트 작업이며 DSN 한 줄 변경만으로 완료된다고 가정하지 않는다.

### 4.3 포트 배치

toy-tune의 기존 `SourceReader`, `DatasetStore`, `ArtifactStore`, `RunStore`, `EnvironmentInspector`를 유지한다. `KnowledgeReader`, `PacketReader`, `TrainingEngine`, `GenerationEngine`은 기존 교체 계약이며 실제 기능은 구현 현황을 따른다.

추가 설계는 소설 문체용 `StyleEncoder`, 지식 의미 검색용 `SemanticEncoder`, 필요 시 `StyleReferenceReader`다. 공개 쓰기는 작품 관리 영역의 별도 `PublicationRepository`/unit-of-work 계약으로 설계한다. 읽기 port나 학습 engine에 정사 쓰기 권한을 추가하지 않는다. 이 명칭들은 후속 구현 제안이지 현재 존재하는 API 목록이 아니다.

핵심 역사 설계의 목표 계약은 다음과 같다. 모두 후속 구현 대상이며 toy-tune 내부에 넣지 않는다.

| 책임/계약 | 역할 |
|---|---|
| Anchor Manager / `PlanRepository` | 앵커·역사표 revision·승인 범위·잠금을 저장하고 승인된 변경만 수락 |
| Backward Planner / `PlanningModel` | SOTA가 선행 조건과 복수 경로를 역산하고 보조 사건을 제안 |
| Causality Engine / `CausalAssessor` | 구조화 관계 탐색과 SOTA 의미 판정을 조합하여 정방향 영향·모순을 보고 |
| Constraint Validator | 참조·날짜 순서·명시된 자원 제약·승인 revision을 프로그램으로 검사 |
| Scene Context Compiler | 잠긴 역사표와 공개 정사에서 장면 명세·허용 사실·금지사항을 동결 패킷으로 구성 |

승인·잠금·revision 검증은 application/domain이 통제한다. SOTA 응답은 제안이며 SQL 실행·계획 승인·잠금 해제 권한이 없다. SQLite/PostgreSQL adapter는 같은 의미의 조회·승인 계약을 구현한다. 벡터 확장이나 그래프 제품이 인과율 엔진 자체를 대신하지 않는다.

모델 선택은 composition 설정의 역할 정책으로 검증한다. Gemma 운영 `GenerationEngine`과 SOTA `comparison_writer`는 같은 생성 요청 의미를 공유할 수 있지만 별도 profile로 실행한다. 기획·검수·추출은 application이 소유하는 역할 계약 뒤에 SOTA adapter를 연결하고 SQL·공개 권한은 주지 않는다. Munche와 Granite는 별도 encoder/profile/index로 연결한다. 지식 파이프라인이 문체 encoder로 자동 fallback하지 않는다. 기술 교체 가능성이 확정된 모델 역할을 임의 변경할 권한을 뜻하지 않는다.

## 5. 원본, 원장, 파생 저장소

| 논리 자산 | 보존할 원본 | 조회·검색용 파생물 |
|---|---|---|
| 원역사·과학 지식 | 영어 우선 자료 snapshot, 출처·교정 기록, 승인된 구조화 릴리스 | `original.sqlite`, FTS, Granite 의미 벡터 |
| 작품 역사 설계 | 앵커, 후보·승인 역사표, 조건·보조 사건, 영향 검토, 승인·변경 이력 | 계획 조회·의존 관계 인덱스, 장면 명세 패킷 |
| 작품 정사 | 공개 본문 bundle, 역사전표, 공개 확인·수락 기록의 순서 | 작품별 `canon.sqlite` 조회 테이블, 요약·기억 벡터 |
| 문체 | 지정 원문과 사용 범위, split·reference manifest | 문체 벡터 파일, 필요 시 `style.sqlite` |
| 학습 | source bundle, dataset manifest, 모델·실행 계보 | token cache, 임시 checkpoint |

정사의 권위는 승인·공개 확인된 원장 항목과 그 순서에 있다. SQLite를 단순 캐시로 취급해 유일한 수락 기록까지 지우지 않는다. 원장은 DB 안에 저장할 수 있지만, 원장·수락 기록·본문 bundle을 포함한 검증된 export/백업이 있어야 조회 DB를 복원할 수 있다.

파일명은 물리 배치 예시다. 초기에는 작품별 SQLite가 자연스럽지만 PostgreSQL에서는 `work_id`와 schema/table로 동일 경계를 구현할 수 있다. 문체 저장소와 정사 저장소의 동시 트랜잭션은 요구하지 않는다.

## 6. 원역사 구축과 온톨로지

### 6.1 단계별 구축

자료 snapshot → 결정적 문서·절 파싱 → 출처 연결 → SOTA의 엔티티·사건·관계 후보 추출 → 프로그램 검사·사람 교정 → 원역사 릴리스 → 검색 인덱스 순서다. 첫 파일럿은 작품에 필요한 시대·인물·지역의 작은 자료 묶음으로 한다. 전 역사 덤프는 후속 확장이다.

영어 위키백과를 우선한다. 원문 덤프 확보·로컬 검색과 SOTA의 전체 구조화는 별도 작업이다. 원문을 보관한 뒤 필요한 자료만 SOTA로 정제한다. 전체 원문 번역이나 전체 문서의 SOTA 분석을 첫 검색의 선행 조건으로 만들지 않는다. 한국어 등 다른 언어 문서는 보완 자료로 추가하며 Wikidata ID로 연결해도 언어별 원문·revision·서로 다른 주장은 보존한다.

수집 경로, 영어 문서 파일럿, Granite 97M/311M 비교와 비용 측정은 [영어 위키백과·Granite 지식 구축 계획](./plans/20260914-enwiki-granite-knowledge-ingestion-plan-v0-1.md)을 따른다. 문서의 전체 편집 이력이 아닌 최신 본문 snapshot을 기본으로 한다.

위키백과는 출처 자료이지 ‘전체 역사의 완전한 진실’이 아니다. 추출 결과에는 근거 절·원문 범위·추출기 revision·검토 상태를 남긴다. 출처 간 모순, 불확실한 연대, 누락은 그대로 표현하며 모델이 만든 연결 관계를 사료 사실로 승격하지 않는다.

원역사 릴리스는 발행 후 불변으로 취급한다. 교정은 새 릴리스로 발행하고 작품은 사용 중인 `original_release`를 고정한다. 새 릴리스 적용은 기존 override 참조와 작품 정사에 대한 영향 검토 후 별도 작업으로 수행한다.

### 6.2 논리 스키마

- 문서·절: source ID, 언어, 원자료 revision, 본문 hash, 출처, 사용 조건.
- 엔티티: 안정 ID, 유형, 별칭, 외부 ID, 등장 근거.
- 사건·사실: 대상, 내용, 유효 시간 범위, 날짜 정밀도, 지역, 검토 상태.
- 관계: 양 끝의 ID·유형, 관계 유형, 유효 기간, 출처, 추출/검토 이력.
- 판정: 관찰·추론·창작 제안 구분, 사용 근거, 판정자/도구 revision.
- 상태·조건·자원: 어떤 시점에 무엇이 가능하고 부족한지, 보유 주체·지역·유효 기간·단위·근거. 미확인은 부재나 불가능과 구분한다.
- 인과 관계: `requires`, `enables`, `prevents`, `consumes`, `produces`, `changes` 등 선행 조건·효과. 출처가 명시한 관계, SOTA의 해석, 작품의 창작 가정을 구분한다. 단순 선후·동시 발생·문서 링크를 인과 관계로 자동 승격하지 않는다.

기존 Original RDB v1의 문서·절·엔티티·사건·관계·판정 이력 구분은 재사용한다. PostgreSQL DDL과 벤더 이름이 들어간 판정 enum은 그대로 복사하지 않는다. `ontology_version`과 별도의 모델 계보로 관리한다. 날짜는 일자 하나로 강제하지 않고 연·월·기간·불명 상태를 보존한다.

관계 탐색은 시간·지역·대상으로 좁힌 제한 깊이 탐색부터 검증한다. 순환·중복·탐색량 상한을 관리하며 최단 경로를 역사적 인과의 증명으로 취급하지 않는다. 온톨로지 변경 시 기존 데이터의 검증·이관을 명시한다.

과학 자료는 현재 알려진 원리, 역사적 발견·전파 시점, 실제 구현 조건, 작품 인물의 지식을 구분한다. 현대 자료에 기술 설명이 있다는 이유로 과거 인물이 이를 알고 제작할 수 있다고 간주하지 않는다. 제작 조건·기술 도입 가능성의 SOTA 추론은 출처 사실과 별도 상태로 보존한다.

### 6.3 작품 기간과 원역사 검토 완료

작품 기간(예: 1453~1600)을 먼저 지정하고, 해당 기간의 역사·과학·인물과 필요한 이전 배경을 검토한 뒤 실제 집필을 시작한다. 이 사용 범위에는 미검토 원역사가 없다는 것을 집필의 전제로 삼는다. 기간, 포함 자료·사실 ID, 배경 참조, `original_release`, 범위 revision과 검토 완료 상태를 기록한다. 원역사 전체를 작품마다 복제하지 않고 공용 자료를 참조한다.

검토 완료는 지정 범위의 자료 검토가 끝났다는 의미이며, 사료의 불확실성·상충하는 주장까지 제거하거나 실제 역사의 모든 사실을 확보했다는 의미가 아니다. 자료·기간 확대나 원역사 릴리스 변경은 해당 범위의 검토 완료 상태를 다시 확인한 뒤 집필에 적용한다. 초기 원역사 검토 완료가 후속 개변의 영향 검토를 대신하지 않는다.

자료 구축·검색 파일럿은 미검토 원자료로 진행할 수 있지만 실제 집필의 근거로 바로 사용하지 않는다. 작품 개변으로 재검토가 필요한 사실은 §7.2의 `contested`로 처리하고, 관련 검토가 끝나기 전까지 확정 집필 근거에서 제외한다.

## 7. 작품별 단일 정사와 시간

### 7.1 세계선과 작업 분기의 구분

공용 원역사 한 기준선 위에 작품별 공개 정사 하나를 유지한다. 1,000화의 전표가 있어도 영구 세계선이 1,000개 생기는 구조가 아니다. Git commit, 집필 worktree, 역사전표, 정사 revision은 서로 다른 식별자다.

집필 중에는 `base_canon_revision` 위에 임시 delta를 올려 검토할 수 있다. 공개 후 승인된 delta만 선형 정사에 합친다. 작업이 끝난 worktree 정리는 보존·반영 확인 이후 별도로 하며 SQLite 바이너리를 Git merge하지 않는다.

작품의 역사표는 먼저 설계되고 본문은 이를 구현한다. 작품 안에서 다음 지위를 구분하며, 이를 각각 영구 세계선으로 만들지 않는다.

| 지위 | 의미 | 변경 권한 |
|---|---|---|
| 후보 역사표 | 역설계 경로·보조 사건·미승인 상세 전표 | 기획 단계에서 수정·폐기 가능 |
| 승인·잠금 역사표 | 앞으로 집필할 사건을 포함하는 집필 명세 | 작가 재승인을 통한 새 계획 revision만 허용 |
| 초안 실현 전표 | 본문에서 추출한 사건과 승인 역사표의 대응 | 검수·재작성 대상, 공개 사실 아님 |
| 공개 역사전표 | 공개된 본문에서 수락된 작품 사실 | 공개 정정 절차로만 변경 |

계획 사건 ID와 공개 사건 ID를 연결하여 예정·서술·수락 여부를 추적한다. 역사표 승인만으로 사건이 이미 일어났다고 조회하지 않는다. 같은 작품 DB 안에 계획과 공개 원장을 별도 테이블로 둘 수 있다. 잠금과 공개는 별도 상태이며 새 계획으로 이미 공개된 역사를 소급 덮어쓰지 않는다.

### 7.2 유효 세계의 계산

질의는 `work_id`, `original_release`, `canon_revision`, `story_time`, 검색 기간과 사용 범위 revision, 필요 시 `pov_character_id`와 `draft_id`를 명시한다. 계획을 사용하는 질의는 `plan_revision`과 용도(기획/집필/공개 사실 조회)를 추가한다. 작품 전체 기간, 이번 질의의 검색 기간, 장면 시점과 인물 인지는 서로 다른 조건이다.

유효 세계는 해당 시점의 원역사 기준선에 공개 사건·활성 사실 전표를 적용하고 override를 해석한 결과다. 초안 delta는 요청된 집필 세션에서만 추가하며 공개 조회에 섞지 않는다.

- `active`: 해당 질의에서 사용 가능한 기준 사실.
- `contested`: 개변 영향으로 재검토가 필요한 사실. 확정 근거로 사용하지 않는다.
- `overridden`: 명시적 변경으로 원래 형태가 적용되지 않는 사실.

override 효과는 취소·변형·지연·앞당김·대체 등을 구분한다. 변경 대상, 적용 시간·범위, 대체 사실, 근거를 연결한다. 지연된 사건은 단순 삭제로 처리하지 않는다. 개변 이후의 모든 원역사를 일괄 폐기하지도, 모두 예정대로 일어날 것으로 확정하지도 않는다.

### 7.3 네 가지 시간과 세 가지 시야

- 사건/사실의 유효 시간: 세계 안에서 언제 일어났고 언제까지 유효한가.
- 서술 회차: 어느 화에서 서술되었는가.
- 공개·정사 수락 시간: 독자 공개와 내부 반영이 각각 언제 확인되었는가.
- 인물 인지 시간: 인물이 언제 어떤 경로로 알았는가.

인지 기록은 전지적 사실의 복사본이 아니다. 믿음·오해·소문과 실제 사실을 구분하고 정보 획득 경로를 둔다. 미래 정보 보유 설정도 예외 규칙으로 명시한다.

기획자는 미래 앵커를 볼 수 있지만, 집필자는 현재 장면의 허용된 정보만, 인물은 자신의 인지 범위만 사용한다. 전지적 서술인지 제한 시점인지도 패킷 정책에 반영한다. 회상·뒤늦은 공개 때문에 사건 시간과 공개 revision을 같은 것으로 취급하지 않는다.

## 8. 핵심: 역방향 인과 추론·역사표 창조·구속력 있는 집필

### 8.1 목적론적 역사 설계

작가가 원하는 결말을 먼저 정하고, 그 결말이 서사 안에서 납득되도록 현재와 미래 사이의 사건·조건을 설계한다. 실제 역사의 미래를 예측하는 시뮬레이터나 객관적 필연성을 증명하는 장치가 아니다. Backfilling은 예외적인 오류 보정이 아니라 핵심 창작 기능이다.

원역사는 출발 상태와 근거를 제공한다. 작품 역사표는 원역사에서 달라질 사건까지 의도적으로 창조한다. 근거 없는 내용을 원역사에 넣는 것은 금지하지만, 작품의 창작 사건까지 금지하지 않는다. 창작 사건에는 채택 이유·선행 조건·후속 효과를 연결한다.

### 8.2 앵커 설정과 역방향 설계

1. 작가가 목표 시점 또는 기간, 최종 상태, 반드시 지킬 조건, 허용·금지할 전개를 지정한다. 날짜 유연성은 작가가 명시하며 엔진이 임의로 바꾸지 않는다.
2. 원역사 릴리스와 현재 공개 정사를 고정하고 이미 공개된 사실을 제약으로 읽는다.
3. SOTA가 최종 상태에 필요한 중간 상태·사건·자원·인물 행동을 역으로 분해한다. 한 경로의 조건을 유일하게 가능한 역사라고 단정하지 않는다.
4. 현재 충족한 조건과 부족한 조건, 출처에서 확인되지 않은 조건을 분리한다.
5. 기존 사건의 개변, 인물의 선택, 제도·기술·외교·자연적 사건 등으로 간극을 채울 대안 경로를 제안한다.

앵커 입력에는 `anchor_id`, 목표 시점, 최종 상태, 제약, 작가 의도가 들어간다. 수치형 `required_impact`나 성공 확률 필드는 두지 않는다.

### 8.3 간극 탐지와 Backfilling

간극 보고서는 부족한 조건, 관련 사건·출처, 미확인 사항, 보완 후보, 각 후보가 추가로 요구하는 조건과 부작용을 설명한다. 판정은 `충족 / 부족 / 충돌 / 미확인`으로 표현하며 점수·확률로 환산하지 않는다.

예를 들어 해외 원정이라는 앵커에서 보급 문제가 드러나면 중간 거점 확보, 운송 체계 정비, 현지 협력 세력 형성 등의 사건을 창조할 수 있다. 이는 역사적 사실의 주장이 아니라 창작 후보이며, 선택한 사건이 인물의 동기·정치 관계·시간·자원에 미치는 영향도 검토한다.

보조 사건을 추가할 때마다 그 사건의 성립 조건과 후속 영향을 같은 검증에 넣는다. 편리한 우연이나 대규모 재난을 자동 해답으로 우대하지 않는다. 반대로 작가가 그러한 전개를 선택하는 것은 허용하며 그 선택의 가정과 파급효과를 드러낸다.

대안은 근거, 필요한 준비, 등장인물의 동기, 희생·부작용, 다른 앵커와의 충돌, 작가가 원하는 서사 효과로 비교한다. 최단 그래프 경로나 합산 점수로 자동 채택하지 않는다. 탐색 예산 안에서 해결되지 않으면 미해결 간극과 작가의 결정이 필요한 선택지를 반환한다.

### 8.4 정방향 인과율 검증

입력은 공개된 개입 또는 후보 경로 전체다. 둘을 구별하여 후보 검토만으로 공개 정사를 갱신하지 않는다.

1. 행동·보조 사건이 바꾸는 상태·조건·자원을 추출한다.
2. 구조화 관계·SQL/키워드·Granite 검색으로 영향받을 미래 사건 후보를 찾는다. 분야·지역·인물·시간 범위로 탐색을 제한한다.
3. 원자료와 기존 전표를 조회하여 SOTA가 유지·변형·취소·지연·앞당김·대체 필요성을 설명한다. 자료가 부족하면 미확인으로 남긴다.
4. 변경된 조건을 후속 사건에 전파하고 앵커·공개 사실·다른 조건과 충돌하는지 검사한다. 순환·중복·탐색량을 제한하고 미검토 범위를 기록한다.
5. 영향 보고서를 역설계에 돌려보내 사건을 수정하거나 다른 경로를 제안한다. 작가 승인 전에는 후보에만 반영한다.

과거 Domain/Impact/Speed는 각각 분야 태그, 영향을 받는 대상·조건의 설명, 전파 경로·발현 시점·준비 기간으로 바꾼다. 등급이나 속도 점수에서 날짜를 자동 산출하지 않는다. 기간·수량이 필요하면 사료 근거 또는 작품의 명시적 가정과 단위를 기록한다.

프로그램은 알려진 참조·시간 순서·자원 제약·잠금 위반을 검사하고, SOTA는 인물 동기·서사 연결·자료 해석을 검토한다. 어느 쪽도 검토하지 않은 인과관계까지 보장하지 않는다.

### 8.5 상세 역사표와 승인·잠금

채택 후보를 일·주 단위 또는 사건에 적절한 정밀도의 역사표로 구체화한다. 불명인 날짜를 임의의 정확한 일자로 바꾸지 않는다. 전표에는 다음 정보를 둔다.

- 사건 ID, 시점·장소·참여 인물, 예정 사건과 완료 조건.
- 연결 앵커·선행 사건·필요 조건·예상 효과.
- 원역사 유지/개변/신규 창작 구분, 원자료 또는 창작 가정.
- 작가 승인 범위, `plan_revision`, 잠금 상태, 후속 본문·공개 전표 연결.

`후보 → 검토 → 작가 승인·잠금 → 승인된 새 revision으로 대체`라는 계획 이력을 유지한다. 승인된 역사표 전체 또는 작가가 명시한 승인 범위의 모든 전표가 Writer를 구속한다. 중간 사건을 느슨한 참고 가이드로 낮추지 않는다. 승인 범위 밖의 후보는 잠금 상태인 것처럼 전달하지 않는다.

계획 승인은 정확한 역사표 hash와 기준 원역사·공개 revision에 연결한다. 승인 후 변경은 새 후보 revision에서 영향 분석·검토·작가 재승인을 거친다. 작가가 보조 사건 교체를 요구하면 연결 사건·시점·다른 앵커까지 재검토한 결과를 제시하며 엔진이 몰래 목표일을 이동시키지 않는다.

새 계획이 승인되면 영향받는 미공개 초안과 패킷을 재검토 대상으로 표시한다. 공개 게이트는 최신 적용 계획과의 호환성을 다시 검사한다. 계획 승인 시의 공개 revision 이후에 사건이 늘었으면 승인 전제 유지 여부를 검토한다. 공개된 역사는 계획 변경으로 덮어쓰지 않는다.

### 8.6 Gemma 집필과 역사표 실현 검증

1. 잠긴 역사표에서 해당 장면의 목표·필수 사건·금지 전개·완료 조건을 고른다.
2. 고정된 원역사·공개 정사·계획 revision으로 장면 패킷을 만든다. 현재 사실, 이번 장면에서 실현할 계획, 인물의 인지, 서술 허용 범위를 분리한다.
3. 직전 문맥과 필요한 문체 예문을 붙여 Gemma가 대사·묘사·장면을 작성한다. 역사표와 충돌하지 않는 표현·구성은 Writer의 자유다.
4. SOTA가 본문에서 실현된 사건을 추출하여 계획 사건 ID와 대응시킨다. 필수 사건 누락, 금지 사건 추가, 날짜·인물·상태 변경, 시점 정보 유출을 검수한다.
5. 위반이면 Gemma가 재작성한다. 역사표 자체를 바꿔야 해결되는 경우 집필을 보류하고 기획 변경·작가 재승인으로 돌린다.
6. 역사표에 없는 사실이 추가되면 전표 후보로 표시한다. 후속 역사에 영향을 주는 추가는 인과 검토·계획 변경 승인을 거치고, 비충돌 세부 사실도 공개 승인 전에 확인한다.
7. 본문 수정 후 전표를 다시 추출·검증한다. 통과한 본문과 전표만 공개 게이트로 보내며, 공개 확인 후 작품의 단일 정사에 반영한다.

잠금은 프롬프트만으로 보장하지 않는다. Writer의 계획 쓰기 권한 차단, 프로그램 검사, SOTA 의미 검수, 사람 승인과 공개 게이트를 조합한다. 자동 의미 검수는 누락 가능성이 있으므로 실패·미해결 상태를 통과로 바꾸지 않는다.

기획자는 전체 미래 계획을 볼 수 있다. Writer에는 이번 장면에 필요한 명세를 주되, 그것이 인물의 지식이라는 뜻은 아니다. 요약은 원문을 대체하지 않으며 패킷에 근거·전표 ID를 남긴다. 운영 집필은 Gemma, 역설계·인과 의미 판정·추출·검수는 SOTA다. 이 역할 분리는 상시 에이전트 프로세스나 별도 DB 서버를 요구하지 않는다.

## 9. 내용 검색과 문체 검색

### 9.1 사실 패킷

작품의 검토 완료 범위·검색 기간·시점·revision·인지 범위 필터 → 구조화 사실·키워드 검색 + Granite 의미 검색 → 필요한 관계 확장 → 유효성 재검증 → 중복 제거·토큰 예산 적용 순서로 구성한다. 후보 검색에서 필터를 완전히 적용하지 못했다면 반환 후보에도 같은 규칙을 다시 적용한다.

조사·RAG·관계 탐색은 작품 기간의 자료 집합을 기본 범위로 한다. 기획은 작품 전체 기간을 볼 수 있고, 장면 집필은 해당 시점·선행 사건·지역·주제로 좁힌다. 사건·상태는 발생·유효 기간의 겹침과 선행 관계, 인물은 생존·활동·직위·관계의 유효 기간, 기술은 당시 보급·지역·구현 조건을 사용한다. 기간 이전에 시작되어 계속 유효한 제도·기술·인물을 포함한다. 과학 원리는 관련 주제·적용 조건으로 선별하며, 출처의 작성일을 역사적 유효 시점으로 쓰지 않는다.

전체 역사에서 top-K를 얻은 뒤 기간 밖 결과를 제거하는 방식만을 기본 경로로 삼지 않는다. 범위에 속한 후보 집합을 먼저 정하고 실제 검색량·지연·반환 부족을 측정한다. 한 문서의 대표 연도로 전체 내용을 허용하지 않으며, 사실·관련 원문 구간에 기간과 사용 범위를 연결하고 부모 절·앞뒤 구간 확장에도 같은 규칙을 적용한다. 패킷에는 사용 범위 revision, 요청 검색 기간과 실제 확장 범위를 함께 남긴다.

범위 밖 선행 원인·파급효과 또는 미래 지식·기술 도입 설정의 검토는 대상·기간·이유를 기록한 제한적 확장 조사로 수행한다. 새 자료는 §6.3의 검토를 거쳐 집필에 편입한다. 연대 불명 자료는 자동으로 무관하다고 배제하지 않고 관련성을 검토한다. 연구용 원리·미래 사건의 조회 허용이 인물의 인지나 기술 구현 가능성을 뜻하지 않는다.

한국어 질의→영어 근거 검색을 기본 검증 과제로 둔다. 필요 시 SOTA가 생성한 영어 질의로 검색을 보완하며 원 질의·변환 질의·출처를 기록한다. 영어 FTS가 한국어 질의를 자동으로 이해한다고 가정하지 않는다. 선택 근거는 원문을 유지하고 필요한 한국어 설명만 파생물로 붙인다.

중요 앵커·현재 상태·금지 사실은 벡터 top-K에 들지 않았다는 이유로 생략하지 않는다. 점수가 높은 검색 결과가 override나 인지 제약을 우회할 수 없다. 근거 부족은 빈 결과·불확실성으로 반환하며 만들어 채우지 않는다.

패킷에는 query 조건, 출처·사실 ID, 적용 상태, 계획 revision·잠금 범위·필수 사건·완료 조건, 필요 금지사항, 검색/컴파일 버전, checksum을 담는다. 사실과 집필 명세는 별도 필드로 구분한다. 같은 장면의 여러 질의는 동일 snapshot을 사용한다. 생성 중 정사나 계획이 갱신되어도 사용한 패킷은 바뀌지 않으며 공개 전 재검증한다.

### 9.2 Munche 문체 채널

소설 문체 임베딩은 `Baragi-AI/Munche-768`을 기준으로 하며 `Munche-v2-768`은 후속 버전 비교 대상이다. Munche는 EmbeddingGemma 기반이지만 생성용 Gemma 31B와는 별도 모델이다. 제작자도 일반 의미 검색 모델의 대체재가 아니라고 설명한다. 역사·과학·인물 자료 검색에는 사용하지 않는다. [Munche v2 모델 카드](https://huggingface.co/Baragi-AI/Munche-v2-768)

지식 의미 검색은 Granite가 맡으며 소설 문체 분석과 별도의 품질 기준으로 검증한다. Granite가 미검증·실패 상태이면 구조화·키워드 검색을 사용하거나 근거 부족을 보고한다. Munche를 지식 검색의 대체 경로로 쓰지 않는다.

문체 검색은 우선 사람이 고른 목표 원문/구간에서 출발한다. 장면 개요를 문체 encoder에 넣는 것만으로 목표 작가 문체가 지정된다고 가정하지 않는다. reference bank에서 시점·장면 유형·길이 조건을 맞추고 문체 유사도로 예문 후보를 좁힌다. 소량이면 수동 선택을 유지한다.

생성 모델에는 벡터 자체가 아니라 선택한 예문 텍스트를 전달한다. 예문은 사실 근거가 아니라 표현 참고라고 명시한다. 문체 예문의 인물명·사건 혼입과 원문 복제를 검수한다. 생성 후 후보 재정렬은 문체 지표 검증 이후의 선택 기능이다.

### 9.3 임베딩 공간과 인덱스

Granite 지식 벡터와 Munche 문체 벡터는 별도 공간·collection/index다. 모델/base/tokenizer revision, 출력 차원·차원 축소 설정, prefix, window/stride, pooling, 정규화와 저장 dtype으로 `embedding_space_id`를 식별한다. 같은 차원이라도 서로 다른 모델·revision·전처리의 벡터나 cosine 점수를 직접 혼합하지 않는다.

Granite 97M R2 / 384차원을 첫 기준선으로 두고 311M R2 / 256차원과 같은 영어 자료·질의에서 비교한다. 311M의 차원 축소와 벡터 정규화는 공식 모델 경로로 검증한다. 최종 모델·차원은 영어 대량 덤프 인덱싱 전에 선택하며 초기 기준선을 최종 채택이나 실행 완료로 표시하지 않는다.

SQLite-vector는 기존 결정에 따른 초기 벡터 확장 후보다. 작은 집합은 정확 검색부터 측정하고, 큰 원역사 집합은 배치 인덱스·양자화의 품질/비용을 검증한다. 확장은 adapter 안에 격리하고 지원 OS·빌드·이용 조건을 설치 전에 확인한다. [SQLite-vector 저장소](https://github.com/sqliteai/sqlite-vector)

각 파생 인덱스에는 반영 revision을 둔다. 인덱스가 뒤처지면 새 구조화 사실/미반영 delta를 함께 조회하거나 재구축을 기다린다. 낡은 검색 결과를 최신이라고 표시하지 않는다. 모델 변경 시 새 인덱스를 검증한 뒤 전환한다.

## 10. 공개 게이트와 복구 가능한 정사 반영

아래는 이전 문서의 ‘DB 반영 후 Git commit’ 절차를 구체화한 목표 계약이다. 아직 구현되지 않았다. DB, Git, 파일시스템, 외부 연재 플랫폼을 하나의 원자적 트랜잭션처럼 취급하지 않는다.

### 10.1 공개 단위

불변 publication bundle에 최종 본문, 역사전표, 검수 결과, 부모 정사 revision, 계획·원역사 revision과 각 hash를 포함한다. 사용자 승인은 정확한 bundle hash에 연결한다. 승인 후 본문이나 전표가 달라지면 다시 승인받는다.

상태는 `draft → reviewed → approved → publication_pending → published`로 구분한다. `approved`는 공개 정사가 아니다. `published`는 공개 확인과 내부 원장 반영을 모두 확인한 상태다. 공개 기준이 외부 게시인지 개인용 로컬 확정인지는 작품 설정으로 명시하고, 개인용 로컬 확정을 외부 게시 성공으로 기록하지 않는다.

### 10.2 처리 순서

1. 최종 bundle을 영구 저장하고 hash·복원 가능성을 검증한다.
2. 현재 정사와 `base_canon_revision`을 비교하고 전표 충돌·시간·인지·참조를 검증한다. 적용 계획 revision과 승인·잠금 범위, 필수 사건 실현 여부, 미승인 계획 변경·추가의 부재도 확인한다. 작품별 공개 작업은 한 번에 하나만 진행한다.
3. 동일 bundle에 대한 사람 승인을 확인하고 고유 `publication_id`로 pending 작업을 기록한다.
4. 초기에는 사람이 외부 게시를 수행하고 결과를 확인한다. 게시 확인 ID/시각/본문 hash 등 근거를 기록한다. 자동 플랫폼 게시 기능은 이번 범위 밖이다.
5. 단일 canon DB 트랜잭션에서 부모 정사 revision과 적용 계획 revision·승인 상태를 다시 확인하고 수락 원장, 사건·사실·override·인지 투영, 새 정사 revision, 파생 갱신 작업을 함께 기록한다. 계획 승인 상태와 공개 게이트의 동시성 검사가 가능하도록 작품별 계획 승인 원장과 공개 원장은 같은 트랜잭션 경계에 둔다.
6. 별도 작업으로 검색 인덱스·요약·보존용 Git 이력을 갱신하고 완료 여부를 기록한다. 보존 확인 후 임시 작업 공간 정리를 제안한다.

중복 `publication_id`와 같은 hash의 재시도는 이미 반영된 결과를 반환한다. 같은 ID에 다른 내용이 오면 거부한다. revision 비교와 쓰기는 같은 트랜잭션에 있어야 하며 사전 검사만으로 경쟁을 방지했다고 간주하지 않는다.

### 10.3 실패·변경 정책

- 공개 전 실패: 정사는 바뀌지 않는다. bundle과 실패 원인을 보존한다.
- 외부 공개 후 내부 반영 실패: `publication_pending`을 유지하고 다음 화 공개를 막는다. 게시 여부를 확인해 같은 ID로 복구하며 무작정 재게시하지 않는다.
- 정사 반영 후 인덱스/Git 갱신 실패: 공개 정사를 되돌리지 않고 기록된 작업을 재시도한다. 조회는 반영 지연을 감지한다.
- 40/41화를 병렬 집필: 40화 반영 후 41화를 새 revision으로 재검토한다. 내용·bundle 변경 시 승인도 갱신한다.
- 오탈자 수정과 사실 변경: 본문 버전 변경과 정사 정정 전표를 구분한다. 공개 사실 수정은 `supersedes` 등 연결된 새 기록으로 남기며 과거 이력을 덮어쓰지 않는다.
- 게시 철회: 외부 상태와 정사 유지/정정 여부를 별도 판단한다. 자동으로 과거 revision을 삭제하지 않는다.

이 절차의 장애 주입·중복 처리·복구 테스트가 통과하기 전에는 실제 작품 공개에 사용하지 않는다.

## 11. 문체 학습 공장: toy-tune

### 11.0 선행 소설 분석

사용자가 지정한 리첼렌·간다왼쪽·명원·마늘맛스낵 작가의 보유 소설을 먼저 분석한다. 초기 10~20편 수량보다 작가 선정을 우선하며, 작품별 Luna 분석을 작가별 Sol이 검토하고 루트는 오케스트레이션만 수행한다. 사용자 확정 범위는 구조 지도와 초·중·후반 대표 장면 분석이다. 작품→에피소드→회차→장면을 연결하고, 목표·갈등·선택·대가·관계 변화·정보 공개·복선 회수·보상·문체 특징을 원문 위치와 함께 기록한다. 작가 내 반복 특징과 작품별 차이를 먼저 비교하며, 보유작이 한 편이면 작가 내 반복성은 미확인으로 남긴다. 사용자가 채택한 결과를 기획자의 장면 명세와 Gemma의 학습·평가 기준에 반영한다. 분석 절차와 산출물은 [현행 실행계획 R 단계](./plans/20260918-current-system-execution-plan-v0-1.md), 배정은 [작가별 진행 현황](./research/author-study/README.md)을 따른다.

원문에서 관찰한 특징과 독자 효과에 대한 해석, 판매 성공의 원인 가설은 구별한다. 분석에 쓴 원문은 개발 자료이며 미관측 최종 평가 자료로 취급하지 않는다. 사후 분석의 미래 정보가 학습 입력의 과거 문맥·인물 지식으로 유입되지 않게 한다. 첫 분석은 소수 작품의 대표 구간으로 양식을 확인한 뒤 제공된 전체 작품 집합에 적용하며, 아직 읽지 않은 범위를 명시한다.

### 11.1 원문에서 학습 입력 만들기

정답은 지정한 기존 웹소설 원문의 실제 범위로 고정한다. 입력은 직전 문맥, 장면 조건, 필요 시 당시 허용된 근거 패킷으로 구성한다. 실제 기획 메모와 완성 원문에서 역으로 추출한 질문/개요는 출처 유형을 다르게 기록한다.

장기 목표는 문체뿐 아니라 승인된 역사표·장면 명세를 문장으로 실현하는 능력이다. `legacy/Training Data Pipeline.md`의 의도를 이어받아 원문 씬 확정 → SOTA 사건·장면 정보 추출 → 이전 씬까지의 가상 SOT·인지·문맥 복원 → 이번 장면의 집필 명세 구성 → 원문 정답과 짝짓기 순서로 설계한다. 가상 SOT는 학습 fixture이며 원역사나 운영 작품 정사에 넣지 않는다.

실제 집필과 학습은 현재 사실·필수 사건·금지사항·인지·직전 문맥의 의미 계약과 schema 버전을 공유한다. XML 같은 특정 직렬화 형식의 문자 단위 동일성은 요구하지 않는다. 목표 씬에서 역추출한 사건 개요는 실제 기획자가 제공할 수 있는 수준의 명세로 제한하고 역구성 입력임을 표시한다. 미래 씬의 결과, 정답의 대사·표현을 과거 문맥에 숨겨 넣지 않는다. 최소 문체 토이 이후 이 조건부 집필 학습을 별도 단계로 추가한다.

역질문·개요 추출은 SOTA 모델이 맡고, 원문 표현을 그대로 질문에 복사하거나 배포 때 알 수 없는 정보를 조건에 숨기지 않도록 검사한다. 정답 원문은 변경하지 않는다. 학습에 사용한 문맥과 실제 집필 입력의 차이도 평가한다. 단순 문체 토이는 근거 패킷 없이 시작할 수 있다.

split을 먼저 정하고 같은 장면·겹치는 window·파생 질문·변형본을 같은 split에 묶는다. 원문 hash·범위와 질문 생성기/템플릿 revision을 보존한다. 목표 작가의 시간순 holdout과 다른 작가 일반화 평가는 별개로 설계한다. 문체 reference bank는 train에서만 구성한다.

### 11.2 학습 실험 순서

첫 실험은 baseline 생성 → 최소 학습 step → 짧은 LoRA 학습 → adapter 저장 → 새 프로세스 재로드 → 같은 조건 평가다. tokenizer·chat template·정답 loss mask와 학습 가능한 파라미터를 실제 모델에서 확인한다. 필요한 dtype·sequence length·batch/rank는 모델 지원과 메모리 실측 후 정한다.

운영 생성 계열은 Gemma로 확정하고 주 목표는 Gemma 4 31B 및 선택한 heretic/uncensored 변형이다. 작은 토이 모델도 Gemma 계열에서 고른다. 정확한 체크포인트와 revision은 실행 전에 확정한다. Stabhappy GGUF는 기존 조사에서 추론 비교 대상으로 다뤘으며, 학습 주경로는 검증된 원본 가중치와 adapter다. 과거 모델 카드 조사만으로 현재 파일 계보·학습 지원을 보장하지 않는다.

continued pretraining, rsLoRA/QLoRA 비교, abliteration 순서 비교, 선호 학습은 각각 별도 실험으로 둔다. 첫 실험에 동시에 넣어 문체 변화의 원인을 잃지 않는다. Munche encoder의 LoRA를 생성 모델에 병합하지 않는다.

### 11.3 Munche의 초기 사용

데이터 분포 탐색 → 대표/희귀 문체 구간 검토 → 학습 전후 문체 비교 순서로 적용한다. 점수가 낮다고 원문을 자동 폐기하지 않는다. 원문 문단·문장부호를 보존하며 모델별 전처리를 고정한다.

문체 지표의 순위를 사람의 블라인드 평가와 대조한다. 내용·이름·장르·대화 비율에 의한 혼동을 통제하고 생성문에 대한 편향을 점검한다. cosine을 재현율 백분율로 표시하거나 초기 학습 reward로 직접 사용하지 않는다. 구체적인 v1/v2 비교·window 규약은 [Munche 하위 계획](./plans/20260914-munche-style-embedding-integration-plan-v0-1.md)을 따른다.

### 11.4 실행·모델 계보

`run_id`는 실험, `attempt_id`는 시도다. 소스 hash, dataset/packet/reference hash, base/tokenizer revision, 학습 설정, 환경, seed, step/token 수, 시간·메모리, 평가 조건을 보존한다. tokenizer 토큰 수와 원문 문자 수를 구분한다.

원본 모델 → adapter → 병합본 → 양자화/변환본을 부모 artifact로 연결한다. Mac용 int4 export도 독립 평가 대상이다. CUDA checkpoint의 optimizer 상태를 MLX에서 바로 재개하거나 모든 변환에서 동일 출력을 보장하지 않는다. 양자화 가중치 크기만으로 총 메모리 요구량을 계산하지 않고 문맥 길이·KV cache·실행 overhead를 함께 실측한다.

학습 중 live DB·문체 서비스에 매 step 의존하지 않는다. encoder 배치 작업과 생성용 모델 학습을 나누어 GPU를 순차 사용한다. 재현성 기준은 계보와 허용 오차·품질이며 하드웨어 간 bit 단위 동일성이 아니다.

### 11.5 중간 생성물과 SOTA의 비교 실험

비교는 수동 실행 가능한 독립 use case로 둔다. 학습 전 baseline, 선택 checkpoint, 짧은 학습 완료, 병합·양자화 후, 실제 집필의 선택 장면/회차에서 호출할 수 있어야 한다. 매 step이나 매 화의 필수 유료 호출로 만들지 않으며 비교 시점·샘플 수·비용 상한은 설정으로 지정한다.

각 `comparison_id`는 한 번 고정한 과제·입력을 여러 writer에 전달한다. 비교군은 원본 Gemma, 해당 Gemma checkpoint/adapter, 선택한 SOTA writer다. 장면 지시·직전 문맥·사실/문체 패킷·계획 revision·목표 분량·도구 접근 조건을 같게 한다. 벤더별 chat template은 달라도 의미 입력은 동일하게 유지하고 변환 내용을 기록한다. token 수나 seed가 같다는 이유로 서로 다른 모델의 조건이 완전히 같다고 가정하지 않는다.

- 기본 비교는 각 writer의 독립 초안이다. SOTA에 Gemma 초안을 보여주고 고치게 한 결과를 독립 생성 기준선으로 섞지 않는다.
- 검수·재작성까지 비교할 때는 별도 실험으로 표시하고 동일한 검수 rubric·수정 기회·비용 한도를 적용한다. Gemma 운영 수정은 계속 Gemma가 맡는다.
- 문체, 가독성, 장문 연결성, 정사·인지·지시 준수, 반복·원문 복제, 비용·지연을 따로 기록한다. Munche 점수만으로 승자를 정하지 않는다.
- 사람은 모델명을 가린 결과를 순서 무작위로 비교한다. SOTA judge를 보조로 쓰면 평가 순서를 교환하고 생성 모델과 judge의 관계를 기록한다. 가능한 경우 독립 judge를 사용하며 자기 모델 선호와 기획자/검수자 중복 편향을 사람 평가로 점검한다.
- exact model/version, provider 응답 모델 ID, 요청·출력 hash, packet/dataset/encoder revision, decoding 설정, 평가 rubric·judge version, 실제 비용·지연을 보존한다. 버전 고정이 불가능한 API는 호출 시점과 한계를 명시한다.
- SOTA가 바뀌면 같은 과제에서 새 비교를 추가한다. 기존 결과를 덮어쓰거나 기준선 갱신과 Gemma 개선을 혼동하지 않는다. 실패·거절·분량 초과도 결과로 남긴다.
- 반복 비교는 validation/development 집합에서 수행한다. 최종 test는 모델·설정 선정 후 별도 평가하고 결과를 다시 튜닝 입력으로 사용하지 않는다.

SOTA 비교 출력과 검수 결과는 평가 artifact다. 원문 정답·학습 데이터·정사에 자동 넣지 않는다. 합성 데이터 활용은 후속 별도 결정이다. API 접근이나 전송 승인이 없으면 비교를 `not_run`으로 남기고 Gemma 실험 결과와 구분한다. 계정 연결·유료 호출·원문 전송은 이 문서 수정으로 실행하지 않는다.

작품 관리·지식 구축 코드는 필요한 첫 use case를 구현할 때 독립 책임으로 배치한다. 공통 대형 `shared` 패키지나 모노레포 루트 venv에 의존하지 않는다. 프로젝트 간에는 버전 있는 파일/데이터 계약을 우선하고 `sys.path`로 형제 프로젝트 내부를 가져오지 않는다.

현재 toy-tune은 작은 source bundle을 dataset에 함께 보존한다. 위 sources 분리·중복 제거·publication 구조 전체가 이미 구현된 것은 아니다. 기존 작품 파일을 자동 이동하거나 Git 이력을 재구성하지 않는다.

## 13. 배포·운영·보안

### 실행 조합

- 로컬 맥북: 원문 선택, 설정, 검토, 데이터 준비. 초기에는 GPU/DB 없이 CPU 계약 검사를 실행한다.
- Backend.AI H200: 확인된 세션에 SSH로 접속하고 동일 toy-tune 소스·동결 입력을 실행한다. GPU 할당 사실과 Python/Torch/마운트·용량·접속 검증은 구분한다.
- 다른 GPU: 같은 코드·입력 artifact와 검증된 환경으로 별도 attempt를 실행한다.
- Mac 생성: 모델·변환·MLX 지원 검증 후 채택한다. 저장된 문체 벡터를 읽는 것과 새 문장의 Munche 임베딩을 만드는 것은 다른 capability다.
- PostgreSQL: 선택된 호스트에서 읽기 전용 snapshot을 추출하거나 조회한다. DB와 GPU가 같은 네트워크/머신이라는 가정을 두지 않는다.

### 영속성과 복구

활성 SQLite는 검증된 로컬 파일시스템에서 사용한다. WAL은 네트워크 파일시스템에서 동작하지 않으며, 여러 attached DB의 갱신도 DB 전체에 걸쳐 한 번에 원자적이지 않다. 따라서 정사 핵심 트랜잭션은 한 DB에 모으고 원역사·문체 인덱스와의 동시 원자성을 요구하지 않는다. [SQLite WAL 문서](https://www.sqlite.org/wal.html)

Backend.AI vfolder의 파일시스템을 확인하기 전 활성 WAL DB 배치를 확정하지 않는다. 일시 디스크는 작업용일 뿐 유일한 정사 원장·원문·최종 adapter를 보관하지 않는다. 실행 중 DB를 단순 파일 복사하는 대신 일관된 snapshot을 만들고 복원 검사한다.

checkpoint·bundle은 임시 기록 후 checksum·완료 표식으로 발행한다. 부분 산출물은 소비하지 않는다. 같은 run/publication에 한 writer만 허용하며 다중 호스트에서는 로컬 lock만으로 안전하다고 간주하지 않는다. 강제 종료 뒤 프로세스·완료 표식·유효 checkpoint를 확인하고 재개한다.

원문, 공개 bundle·원장, 채택 모델은 별도 사본을 보존한다. 캐시와 파생 인덱스는 복구 우선순위가 낮다. 백업 성공뿐 아니라 작은 fixture의 DB 재생성, dataset checksum, adapter 재로드를 확인한다. 복구 시간 목표는 실측 후 정한다.

### 접근 경계

명시적으로 선택한 파일만 전송한다. SSH 키·HF token·DB credential은 Git·로그·resolved config에서 제외한다. 학습/생성은 계획·정사 읽기 전용, 계획 승인·잠금 변경은 계획 승인 use case, 공개 정사 쓰기는 공개/정정 use case에만 부여한다. 외부 모델/API 전송은 사용자가 허용한 범위에 한정하며 로깅 서비스는 기본 비활성화한다.

원문·자료 속 명령문은 데이터다. 검색 결과나 모델 출력이 파일 삭제, DB 쓰기, 외부 게시를 지시할 권한을 갖지 않는다. 실제 모델 접근 조건과 원문 이용 범위를 확인하고 원문·파일명·provenance·생성물까지 비공개 자산으로 취급한다.

## 15. 현재 구현과 단계별 진행

### 15.1 로컬에서 확인한 구현 범위

2026-09-14의 `toy-tune` 소스와 구현 문서 기준이다. 이번 문서 재작성에서 GPU 실행이나 테스트 재실행을 했다는 뜻은 아니다.

- 구현: 독립 Python 패키지, CLI 조립, runtime 설정·환경 inventory, 지정 source bundle 검증, 시간순 split, 불변 파일 dataset·checksum, 파일 artifact/run 상태 저장소.
- CLI: `doctor`, `prepare`, `verify-dataset`만 존재한다.
- 제한: 현재 prompt는 입력 bundle에 제공한다. 질문 자동 생성, 실제 packet 반입, tokenizer/loss mask 검증은 미구현이다. `packet_id`가 있는 입력은 현재 거부한다.
- 계약만 존재: 지식 조회/패킷 읽기 및 학습·생성 engine. 실제 CUDA/MLX/SQLite/PostgreSQL adapter가 연결된 것으로 간주하지 않는다.
- 계획만 존재: 앵커 관리·역설계·Backfilling·정방향 인과 검토·역사표 승인/잠금·장면 실현 검증, Munche 소설 문체 평가·검색, 영어 위키백과 수집·Granite 지식 검색 비교, SOTA 기획/검수/추출 adapter와 비교 실험, 원역사 구축, 새 정사 공개 게이트. 기존 작품 도구의 기능과 이 목표 구조의 구현 완료를 혼동하지 않는다.
- 이전 구현 문서에는 CPU unittest 28개 통과 기록이 있다. 이는 H200 학습·원격 저장·운영 DB 검증 결과가 아니다.

### 15.2 작업 순서

| 순서 | 범위 | 종료 조건 |
|---|---|---|
| 0. 선행 소설 분석 | 사용자 제공 흥행 소설 10~20개. 구조·인물·정보 공개·문체와 원문 근거 비교 | 채택할 서사/문체 기준, 장면 명세·학습 예시 후보, 분석 범위와 평가 자료 구분 |
| 1. 첫 학습 완주 | toy-tune A~D: 접속·환경 확인, 작은 원문, baseline·짧은 LoRA | 저장·새 프로세스 재로드·동일 조건 비교 |
| 2. 문체 검증 | Munche S0/S1: 작은 원문과 학습 전후 출력 | 사람 평가와 비교하고 채택/보류 결정 |
| 2a. SOTA 비교 | 허용된 소량 입력으로 Gemma baseline/checkpoint와 SOTA 독립 생성 비교 | 입력·모델 계보·비용 보존, 블라인드 평가. 이후 선택 checkpoint·회차에서 재실행 |
| 3. 작은 사실 연결 | toy-tune F + 작품 관리 최소 fixture | 원역사/정사 overlay·인지 필터 → 패킷 → 생성 검증 |
| 3a. 영어 지식 검색 | 영어 위키백과 파일럿 + Granite 97M/311M 비교 | 한국어→영어 근거 검색 품질·처리량·인덱스 비용 검증 후 대량 인덱싱 구성 선택 |
| 3b. 역사 설계 최소 완주 | 작은 앵커와 합성/선택 근거로 역설계→Backfilling→정방향 검토→작가 승인·잠금 | 조건·사건·영향 추적, 변경 재승인, 잠긴 명세를 Gemma가 실현하는지 검증. 전체 덤프 불필요 |
| 4. 한 화 공개 모의실험 | 합성 본문·전표로 공개 게이트 | 경쟁·재시도·장애 복구·원장 재생 통과 |
| 5. 실제 한 화 집필 | 지정 작품·자료, 승인·잠금 역사표, 사람 검토 | 앵커·계획 사건·근거·본문·실현 전표·공개 확인을 추적 가능 |
| 6. 선택적 확장 | 원역사 규모 확대, S2 문체 검색, G PostgreSQL, H Mac | 각 adapter 품질·비용·복구 실측 |

toy-tune E의 경로·패키지 이동성 검사는 초기부터 계속한다. 순서 2의 오프라인 조사는 1과 병행할 수 있다. 이전 보고서의 ‘DB 계약을 먼저 확정’은 의미 규칙을 정한다는 뜻으로 적용하며, 전체 역사 DB 구축을 첫 학습의 선행 조건으로 두지 않는다.

첫 ML 연습을 작게 완주하는 것과 전체 시스템의 핵심이 역사 설계라는 것은 별개의 판단이다. 토이 학습이 핵심 엔진 전체 구현을 기다릴 필요는 없지만, 실제 작품 집필로 확장할 때 역사 설계·잠금 검증을 생략하지 않는다.

### 15.3 미결정 사항

영어 우선 수집, Gemma 운영 생성, Munche 소설 문체 전용, Granite 지식 의미 검색 비교, SOTA 기획/검수/추출 및 비교 경로는 확정이다. 실제 학습 원문·범위와 권한, Gemma base/adapter revision, H200 이미지와 디스크, 목표 문맥 길이, Munche v1/v2 선택, Granite 97M/384와 311M/256의 최종 선택, 역할별 SOTA 모델·호출 예산·외부 전송 범위, 공개 기준/수정 정책, 맥북 사양·지원 엔진, PostgreSQL이 필요한 규모는 실험 단계에서 확정한다.

이 문서 작성은 코드 구현·모델 설치·자료 업로드·DB 이관·공개 자동화 승인이 아니다. 다음 구현은 해당 단계의 범위와 검증 조건으로 진행한다.
