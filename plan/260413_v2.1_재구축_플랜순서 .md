## 1. 설계 원칙 (v2에서 처음부터 관철할 것)

### 1.1 클린코드 (greenfield에서의 의미)

1. **레이어 경계 엄수**: 헥사고날 대칭 구조. 의존성 방향은 다음과 같고, 역방향 import 금지. CI에서 `import-linter` 로 강제.
   - `domain → ports`
   - `services → domain, ports`
   - `pipelines → domain, ports, services`
   - `use_cases → domain, ports, services, pipelines` (Primary application entry)
   - `adapters/outbound → domain, ports` (Driven: ports 구현체)
   - `adapters/inbound → domain, use_cases` (Driving: use_case 를 구동. ports/services/pipelines 직접 import 금지)
   - `container.py` 만이 위 전부를 import 가능 (와이어링 지점)
2. **의존성 역전**: 모든 외부 경계(SQLite, LLM, 파일시스템, 시계)는 Protocol 뒤. Container에서만 실체 와이어링.
3. **순수 도메인**: `domain/`은 표준 라이브러리 이외 import 금지. I/O, 글로벌 상태, 싱글톤 일체 불가.
4. **명시적 생성자 주입**: 전역 `_client`, `get_config()` 패턴 **처음부터 만들지 않음**. 컨테이너/팩토리만 허용.
5. **CQS**: command는 반환 없이 상태 변경, query는 순수 조회. 섞으면 리뷰 reject.
6. **Pydantic은 경계에서만**: LLM 응답·파일 I/O·HTTP만. 도메인은 `@dataclass(frozen=True, slots=True)`.
7. **파일 크기 상한**: 초기 단계에서는 300 LOC 경고, 500 LOC 금지. 기존 `state_manager.py` 500+ 라인의 재발 방지.

### 1.1.4 도메인 모델링 절대 룰 (No Compromise — AI-Driven Dev 강제)

§1.1.1~7에 더해, 본 프로젝트는 **1인 + 클로드 코딩** 환경이므로 아래 4개 룰도 동급 강제. "유연" 또는 "케이스 판단"은 클로드의 환각 진입로이므로 허용하지 않음. 작성 비용은 클로드가 부담하므로 0.

**근거 ADR:** Phase 0에서 `docs/adr/0001-result-pattern-and-strict-typing.md` 작성 (의사결정 traceability). 상세 검토는 `plan/260413_v2_클린코드_피드백_검토.md` §7.

8. **Primitive Obsession 절대 금지**
   - 모든 도메인 ID는 `NewType` 정의 (`EventId`, `SceneId`, `ChapterId`, `CharacterId`, `FactionId`).
   - 상태·카테고리·등급은 `Enum` 강제 (`Status`, `Branch` 등).
   - raw `str`/`int`로 도메인 개념 표현 시 PR reject.
   - **검증:** `mypy --strict` + `domain/`·`services/`에서 raw ID 사용 grep → 0건.
   - **닫힌 예외:** 외부 경계(파일 경로, HTTP body, LLM raw 응답)는 raw 허용. 경계 안쪽으로 들어오는 즉시 NewType 변환.

9. **Result 패턴 전면 강제 (도메인 + 서비스 전 영역)**
   - `domain/`과 `services/`의 모든 비즈니스 연산은 `Result[Ok, Failed]` 반환.
   - `Failed` 타입은 반드시 `cause: BaseException | None` 필드 보유 → **스택 트레이스 보존 강제** (진단 정보 손실 방지).
   - **`Failed.cause` 는 opaque diagnostic payload (핵심 계약):**
     - `cause` 는 **진단/로깅 목적 전용**. 도메인 로직 분기에 쓰지 않는다.
     - 오직 `adapters/outbound/proxy/` (LoggingProxy, ObservabilityProxy) 와 `container.py` 만 `cause` 를 **읽어도** 된다.
     - `services/`·`pipelines/`·`domain/`·`use_cases/` 는 `cause` 의 존재를 모른다 (속성 접근 금지, 타입 분기 금지).
     - 분기 필요 시에는 도메인 예외 타입(`Failed.reason` string tag 또는 `Failed` subclass)으로 표현. 인프라 예외 타입(`sqlite3.*`, `anthropic.*`, `httpx.*`)이 코어로 누수되지 않는다.
   - **raise 허용은 닫힌 3개에서만:**
     - (a) `__post_init__` 불변식 위반 (생성자에서 Result 반환 불가)
     - (b) I/O 어댑터 *내부* (DB/네트워크/파일) — 단 service 진입 직전 Result로 wrap. 원본 예외는 `Failed.cause` 에 opaque 담김
     - (c) 프로그래밍 오류 (`assert`, `TypeError`) — 정상 흐름이 아님
   - **검증:** `services/`·`domain/`에서 `raise` grep → 위 (a)~(c) 외 0건. try/except 안 재시도 루프 0건. `services/`·`pipelines/`·`domain/`·`use_cases/` 에서 `.cause` 속성 접근 / `isinstance(..., (sqlite3.|anthropic.|httpx.|openai.))` grep → 0건.
   - **닫힌 예외:** never-fail 순수 함수(예: `x + 1`)는 raw 반환 허용. `Ok(...)` 무의미 래핑 금지. 단 fail 가능성 1%라도 있으면 Result 강제.

10. **횡단 관심사 침투 절대 금지**
    - `services/`, `pipelines/`, `domain/`에서 `logger.*`, `metrics.*` 직접 호출 0건.
    - 실패 진단 정보가 필요하면 `Failed.cause`에 담아 반환 → adapter/proxy 레이어가 로깅.
    - 패턴: `LoggingProxy(MetricsProxy(RealAdapter(cfg)))` Container 와이어링.
    - **검증:** grep → 0건. `logger.exception()` 화이트리스트 폐지.
    - **닫힌 예외:** `container.py`, `adapters/` 내부만 로깅 허용.

11. **God-Config 절대 금지**
    - `config.py`는 단일 거대 객체 금지. 다음과 같이 슬라이스:
      - `AnthropicConfig`, `DbConfig`, `EmbeddingConfig`, `CheckerThresholds`, `PipelineConfig`
    - 각 컴포넌트는 자신이 필요한 슬라이스 타입만 받음.
    - **검증:** 컴포넌트 생성자 시그니처에 god-`Config` 타입 등장 시 PR reject.

12. **CQS DTO 강제 (Command / Query 객체)**
    - `use_cases/` 의 모든 진입점은 **`handle(cmd: Command) -> Result[Ok, Failed]`** 또는 **`query(q: Query) -> Result[View, Failed]`** 시그니처만 허용.
    - `Command` / `Query` 는 `@dataclass(frozen=True, slots=True)` 로 `use_cases/commands.py` / `use_cases/queries.py` 에 정의.
    - 진입점에 raw scalar 파라미터 2개 이상 전달 금지. "편의 오버로드" 금지 — AI가 파라미터를 무한 증식시키는 환각 진입로.
    - **근거:** LLM은 함수 파라미터 순서/개수 혼동이 잦음. DTO 한 덩어리로 묶으면 타입 체커가 필드 누락·순서를 빌드 타임에 차단.
    - **검증:** grep — `use_cases/*.py` 의 public 함수 중 파라미터 수 > 2 → CI fail. `handle(...)` / `query(...)` 외 이름 금지.
    - **닫힌 예외:** 내부 private helper (`_...`) 는 자유. `__init__` 생성자는 DI 주입이므로 제외.

13. **Inbound/Outbound 어댑터 대칭**
    - `adapters/` 는 **`inbound/`** (Driving: CLI, HTTP, Sub-Agent 진입) + **`outbound/`** (Driven: SQLite, LLM, Embedding, FileSystem) 둘로만 분할.
    - `adapters/inbound/` 는 오직 **`use_cases/`** 만 호출. `services/` / `pipelines/` / `ports/` 직접 import 금지.
    - `adapters/outbound/` 는 오직 **`ports/`** 의 Protocol 구현. 역방향 host 호출 금지.
    - **근거:** 헥사고날 대칭. "이 코드는 inbound냐 outbound냐?" 라는 단 하나의 질문으로 배치 결정. AI 혼동 최소화.
    - **검증:** `import-linter` 규칙에 위 의존 방향 박제. 위반 즉시 CI fail.
    - **`scripts/wnw.py` 의 지위:** 플러그인 루트 고정 진입점(Claude Code 의 `${CLAUDE_PLUGIN_ROOT}/scripts/wnw.py` 하드코딩 참조 때문에 이동 불가). 본체 로직은 `src/wnw/adapters/inbound/cli/` 에 있고 `scripts/wnw.py` 는 **sys.argv → adapters.inbound.cli.dispatcher 호출만 하는 10줄 launcher**.

### 1.1.5 계층 책임 명세 (Layer Responsibility Sheet)

§1.1.1 의 의존 방향 외에도, 각 계층의 책임을 아래처럼 **상호 배타적**으로 고정. "이 로직은 어디 두어야 하는가?" 질문을 0초로 결정하기 위함.

| 계층 | 한 줄 책임 | 허용 작업 | 금지 작업 |
|---|---|---|---|
| `domain/` | 비즈니스 불변식·순수 함수 | 값 객체, Enum, 순수 계산, Result 반환 | I/O, 글로벌 상태, 외부 import |
| `ports/` | 외부 경계 Protocol 선언 | `typing.Protocol` 만 | 구현, default 구현, raise |
| `services/` | 단일 책임 도메인 서비스 | ports 호출, 여러 도메인 객체 오케스트레이션, Result 체이닝 | LLM·파일 I/O 직접 호출 (모두 ports 경유), logger/metrics 직접 호출, `Failed.cause` 속성 접근·인프라 예외 isinstance |
| `pipelines/` | 다단계 워크플로 오케스트레이션 | 여러 `services` 순차 실행, `match` 분기, 재시도 한도 | 단일 서비스로 끝날 로직, 비즈니스 규칙 판단 |
| `use_cases/` | **시스템 진입 유스케이스** (트랜잭션 경계) | `handle(cmd) -> Result` / `query(q) -> Result`, `services`·`pipelines` 호출, 선택적 트랜잭션 시작·종료 | 비즈니스 규칙 판단(서비스로 위임), raw 파라미터 2개 초과 |
| `adapters/inbound/` | 외부 트리거 → use_case 호출 | CLI argparse, HTTP 라우트, stdin 파싱, Command/Query DTO 조립 | 비즈니스 로직, ports 직접 호출 |
| `adapters/outbound/` | ports Protocol 의 구체 구현 | DB 드라이버, LLM SDK, 파일 I/O, 프록시 데코레이터 | 비즈니스 룰, 다른 adapter 직접 import |
| `container.py` | DI 와이어링 + lifetime 관리 | 위 전부 import + 실체 주입, proxy 체이닝 | 비즈니스 판단 |
| `config.py` | dataclass 설정 슬라이스 | `AnthropicConfig`, `DbConfig`, … | 로직, env 로딩(IEnvLoader 가 담당) |

**결정 플로우 (AI 가 따라야 할 3문):**
1. "외부에서 들어오는 트리거인가?" → `adapters/inbound/`
2. "외부로 나가는 실제 자원 접근(DB/LLM/FS)인가?" → `adapters/outbound/` (Protocol 은 `ports/`)
3. "둘 다 아니면: 순수 계산이면 `domain/`, 단일 책임 오케스트레이션이면 `services/`, 여러 서비스 엮으면 `pipelines/`, 사용자 기능 단위 진입이면 `use_cases/`."

**`pipelines/` 생성 Trigger Rule (과잉 레이어링 방지):**
- `pipelines/` 에 새 모듈 생성은 **다음 둘 중 하나**를 만족할 때만 허용. 둘 다 아니면 `use_cases/{name}.py` 내부 인라인 오케스트레이션.
  - (a) 2개 이상의 `use_cases/*.handle` 이 동일 워크플로 재사용
  - (b) 단일 `use_case` 의 오케스트레이션이 200 LOC 초과 예상 (§1.1 #7 파일 크기 상한의 실질 위협)
- **근거:** Clean Arch 원론 상 Interactor(Use Case) 가 유일한 오케스트레이터. `pipelines/` 는 재사용 또는 LOC 분할 필요 시의 **유도된 층**이지, 기본 층이 아님. 트리거 없이 양산되면 `use_cases → pipelines → services` 3단계로 응집도 파편화.
- **검증:** PR 리뷰 — `pipelines/` 신규 모듈 추가 PR 은 (a)/(b) 중 어느 조건을 충족하는지 description 에 명시. 누락 시 reject.
- **현 플랜 상태:** `pipelines/scene_generation.py` 1개는 (b) 충족 (집필 루프 SOT fetch → vector fetch → LLM → XML validate → 자가 교정 → fact extractor → 3법칙 → retry 체인이 200 LOC 확실히 초과). 유지.

**서비스 vs 파이프라인 vs 유스케이스 판정 룰 (3층 경계 모호성 해소 — 5차 리뷰 반영):**

`quality_reviewer` (6체커 오케스트레이션), `context_builder` (쿼리 라우팅 + 엔티티 링킹 + 리랭킹), `fact_extractor` (LLM 2차 호출 + SOT 대조) 같은 **복합 오케스트레이션 서비스**가 pipeline/use_case 와 구분되는 기준을 다음 체크리스트로 고정:

| 신호 | 판정 |
|---|---|
| (ㄱ) 외부 트리거(CLI/HTTP/Sub-Agent) 의 **기능 단위 진입점**인가? | Yes → `use_cases/` |
| (ㄴ) 2개 이상의 `use_case` 가 동일 순서로 호출하는 **재사용 워크플로**인가? | Yes → `pipelines/` |
| (ㄷ) 단일 use_case 내부이지만 오케스트레이션이 200 LOC 초과 예상인가? | Yes → `pipelines/` 로 추출 |
| (ㄹ) 위 셋 모두 No, 단일 도메인 책임 + 여러 ports/domain 객체 엮음 | → `services/` |

**예시 적용:**
- `quality_reviewer` → (ㄱ) No, (ㄴ) No (review use_case 1개만 호출), (ㄷ) 경계값 — 6체커 병렬 실행 자체는 30 LOC 내외. **services/** 유지.
- `context_builder` → (ㄴ) Yes (`write` + `plan` + `query` 3개 use_case 가 재사용). **pipelines/ 로 승격 후보** — Phase 4 착수 시점에 use_case 소비 패턴 재확인 후 결정. Phase 4 상세 문서 DoD 에 판정 결과 기록 요구.
- `fact_extractor` → (ㄱ) No, (ㄴ) No (scene_generation pipeline 내부에서만 호출), (ㄷ) No. **services/** 유지.

**Services 간 수평 호출 규칙 (순환 방지):**
- `services/` 내부에서 같은 계층의 다른 service 호출은 **단방향 그래프**로만 허용. 순환 발생 시 공통 로직을 `domain/` 으로 내리거나 `pipelines/` 로 올림.
- **허용 방향 선언:** `context_builder → entity_linker`, `context_builder → genre_profile`, `context_builder → style_sampler`, `context_builder → writing_guidance`, `quality_reviewer → checkers/*`, `workflow → snapshot`. 위 목록 외 수평 호출은 PR description 에 근거 명시.
- **검증:** `import-linter` 커스텀 규칙 — `services/A` → `services/B` 호출 시 B가 A 를 역으로 import 불가. 순환 즉시 CI fail.

**Aggregate 경계 + Unit of Work (cross-repo 트랜잭션 원자성):**
- SOT 저장은 `SotEvent`(`IEventRepo`) · `Scene`(`ISceneRepo`) · `Character/Faction`(`IEventRepo.upsert_entity`) 가 **하나의 트랜잭션**으로 묶여야 하는 경우가 있음 (예: fact_extractor → 이벤트 추가 + 신규 캐릭터 등록).
- `ports/unit_of_work.py`: `IUnitOfWork` Protocol — `__enter__` / `__exit__` / `commit()` / `rollback()` + `events: IEventRepo` / `scenes: ISceneRepo` / `state: IStateRepo` 속성 제공. 모든 repo 는 UoW 컨텍스트 안에서만 쓰기 허용.
- `use_cases/` 만 `IUnitOfWork` 를 열고 닫는다. `services/` · `pipelines/` 는 주입받은 UoW 또는 개별 repo 만 사용.
- **검증:** `services/`·`pipelines/` 에서 `IUnitOfWork.commit()` / `rollback()` 호출 grep → 0건. 쓰기 연산은 반드시 use_case 트랜잭션 경계 내부.

**Command/Query DTO 파싱 경계 (Pydantic ↔ frozen dataclass 2단계):**
- `adapters/inbound/cli/` 는 argparse → **직접** frozen dataclass Command 조립 가능 (스칼라 인자뿐, 타입 안전).
- `adapters/inbound/http/` (미래) · LLM 구조화 응답 파싱 · stdin JSON 입력은 **Pydantic BaseModel 로 파싱 → `.to_command()` 메서드로 frozen dataclass 변환** 2단계. Pydantic 모델은 `adapters/inbound/*/schemas.py` 에만 존재.
- **근거:** Pydantic 은 경계 검증용(§1.1 #6). 도메인·유스케이스는 frozen dataclass 로 불변성 강제. 두 표현을 1:1 매핑하여 경계 누수 차단.
- **검증:** `use_cases/commands.py` · `queries.py` 에 `pydantic` import → fail. `adapters/inbound/**/schemas.py` 외 Pydantic `BaseModel` 정의 → fail.

### 1.2 TDD (Greenfield 룰)

1. **모든 기능은 Red로 시작**. 테스트 없는 코드 머지 금지.
2. **테스트 피라미드**:
   - Unit (`domain/`, `services/` 순수 로직): 수백 개, ms 단위, 80%+ 커버리지.
   - Integration (`adapters/`): 인메모리 SQLite + fake LLM, 수십 개.
   - E2E (`skills/` 골든 패스): 3~5개. CI 총 1분 이내.
3. **동치성 테스트 (Equivalence)**: v1 포팅 모듈은 "같은 입력 → 같은 출력" 회귀 테스트를 별도 suite(`tests/equivalence/`)로 유지.
4. **LLM/임베딩 실제 호출 금지**: `tests/fakes/`에 fake adapter. API 호출은 E2E 계약 테스트(수동 트리거)에만.
5. **리팩토링 정의 준수**: 행위 변경은 기능 추가 PR, 구조 변경은 refactor PR. 한 커밋에 섞지 않음.

### 1.3 포팅 규율 (v1 → v2 이식 규칙)

1. **먼저 읽고, 이해하고, 테스트 쓰고, 다시 작성**. 복붙 금지. 대부분의 v1 코드는 시그니처/타입만 참조.
2. **동일 동작 포팅이 끝난 모듈만 `v1`에서 제거 대상 후보**. 폐기는 Phase 마지막에 일괄.
3. **스키마는 v1과 동일하지 않음**: 피드백 문서의 DAG/branch/provenance 필드를 **처음부터** 포함. 대신 v1 DB → v2 DB 일회성 마이그레이션 스크립트 제공.
4. **네이밍은 업그레이드 기회**: v1의 어색한 이름은 v2에서 교정 (`sot_chronology` → `sot_event`, `characters TEXT` → `character_ids FK` 등).

### 2.5 에이전트 체제 보존 (Sub-Agent 셸 + 서비스 백엔드 3층 분리)

v2는 v1의 **Claude Code Sub-Agent 자율성**을 포기하지 않는다. "agents/*.md 를 prompts/checkers/ 로 1:1 이동"이라는 초기 설계는 **퇴화**였고 폐기한다. 대신 3층 분리:

| 레이어 | 위치 | 역할 | 기술 |
|---|---|---|---|
| **Sub-Agent 셸** | `agents/*.md` | Claude Code 진입점. 자율 tool 사용(Read/Grep/Bash), 컨텍스트 격리, 적응형 탐색 | Claude Code Sub-Agent frontmatter + 마크다운 body. body에서 `scripts/wnw.py` CLI 호출 |
| **Python 서비스** | `src/wnw/services/` | 결정론적 백엔드. DB 질의, NewType/Enum 검증, Result 반환 | `mypy --strict` + `IChecker.check() -> Result[CheckReport, Failed]` |
| **내부 프롬프트** | `prompts/checkers/*.md` | 서비스가 LLM **단발 호출** 시 쓰는 템플릿 (Sub-Agent body와 다른 레이어) | 텍스트 자산. 코드에서 로드 |

**호출 흐름 예시 (pacing-checker) — Inbound/Outbound 대칭 반영:**

```
사용자: /webnovel-review 45
  └→ skills/webnovel-review.md (Claude Code Skill)
     └→ Main Claude orchestrator
        └→ Task(subagent_type="pacing-checker")         ← v1 자율성 유지
           └→ agents/pacing-checker.md (Sub-Agent 독립 컨텍스트)
              ├─ [자율] Read 본문/제0045장.md                                    ← 사용자 아티팩트: 직접 허용
              ├─ [자율] Read 개요/권2_기획.md                                     ← 사용자 아티팩트: 직접 허용
              ├─ [자율] Bash: python scripts/wnw.py query entity --name 이설     ← 시스템 SOT(.webnovel/*) 는 CLI 경로로만
              ├─ [자율] Bash: python scripts/wnw.py check pacing --chapter 45
              │         └→ scripts/wnw.py (10줄 launcher)
              │            └→ src/wnw/adapters/inbound/cli/dispatcher.py
              │               └→ adapters/inbound/cli/check.py
              │                  ├─ CheckPacingCommand(chapter=ChapterId(45)) 조립
              │                  └→ use_cases/review.handle(cmd)
              │                     └→ services/checkers/pacing.py
              │                        ├─ IEventRepo.list_by_chapter(ChapterId(45))  ← ports 경유
              │                        │  └→ adapters/outbound/sqlite/event_repo.py
              │                        ├─ ILLMClient.complete(prompts/checkers/pacing.md + context)
              │                        │  └→ adapters/outbound/anthropic/llm_client.py
              │                        └─ return Result[CheckReport, Failed]  ← JSON 직렬화
              └─ Sub-Agent가 결과 해석 + 추가 탐색 판단
```

**강제 규칙:**
- Sub-Agent body는 **비즈니스 로직을 포함하지 않는다**. 오직 오케스트레이션. 모든 결정론적 연산은 `scripts/wnw.py` → inbound CLI → use_case 경로로 위임.
- `scripts/wnw.py` 는 **10줄 launcher**. `sys.argv` 를 `adapters/inbound/cli/dispatcher.main()` 에 그대로 전달만 하고 종료. argparse 정의·로직 0건.
- `adapters/inbound/cli/*.py` 는 argparse 파싱 + Command/Query DTO 조립 + `use_cases/*.handle(cmd)` 호출 + Result → JSON/stderr 변환만 수행 (§1.1.4 #13).
- `use_cases/*.py` 는 `handle(cmd) -> Result` / `query(q) -> Result` 시그니처만. 비즈니스 판단은 `services/` · `pipelines/` 로 위임 (§1.1.4 #12, §1.1.5).
- `services/checkers/*.py` 와 `agents/*.md` 는 **1:1 대응**이지만 **중복 구현 금지**. service가 유일한 로직 소유권자.
- `prompts/checkers/*.md`는 **service 내부용**이다. Sub-Agent는 이것을 직접 읽지 않는다.
- **Sub-Agent 파일 접근 경계 (2차 아키텍처 리뷰 반영):**
  - **직접 Read/Grep 허용 (사용자 아티팩트):** `본문/**`, `개요/**`, `설정집/**` 및 프로젝트 내 사용자가 직접 편집하는 .md/.txt 자산. wnw 도메인 경계 **밖**, 자율 탐색 대상.
  - **직접 접근 금지 (시스템 SOT 영속 데이터):** `.webnovel/**/*.json` (state.json, project_memory.json 등), `.webnovel/**/*.sqlite*`, `.webnovel/checkpoints/**`. 반드시 `scripts/wnw.py query ...` / `wnw status -- --focus ...` / `wnw memory list` 등 CLI 경로 경유. Sub-Agent 는 스키마를 모르는 채로 읽어 drift 시 깨진다.
  - **근거:** 사용자 아티팩트는 wnw 가 소유하지 않는 외부 자원이므로 인바운드 액터의 자율 탐색이 원칙적으로 허용. 반면 `.webnovel/` 하위는 use_case 가 트랜잭션 경계로 감싸는 시스템 소유 상태이므로 Use Case/Query 경로로만 진입.

**효과:**
- v1 Claude Code 플러그인 지위 유지 (marketplace 배포 가능)
- v2 `mypy --strict` + CI grep 검증 + TDD 모두 적용
- Sub-Agent 프롬프트 드리프트와 Python 서비스 회귀를 **따로 리뷰** 가능

### 핵심 설계 결정 (초안 대비 변경점)

- ❗ **순환 참조 "해결" Phase는 없음**. 처음부터 레이어 경계를 import-linter로 강제하므로 순환이 발생하지 않음.
- ❗ **Protocol과 Container를 같이 도입(Phase 2)**. Protocol만 정의하고 Container가 없으면 실사용에서 결국 구현을 직접 import하게 되어 의미 반감.
- ❗ **SOT 확장은 별도 Phase가 아니라 Phase 1 Domain Core의 기본값**. v1 스키마를 먼저 이식한 뒤 확장하는 2단계 비용이 낭비.
- ❗ **v1 동치성 검증**은 포팅 각 Phase(3~7)의 DoD에 내장. Phase 말미에 별도 검증 Phase를 두지 않음.

## 5. 포팅 전략 (v1 → v2)

각 포팅 Phase에서 동일 프로세스 적용:

1. **Read**: v1 대상 모듈 전체 정독. 숨은 side effect·암묵 의존성 노트화.
2. **Spec**: 동작을 시나리오 목록으로 추출. 입력/출력/불변식.
3. **Red**: 시나리오마다 v2에서 실패하는 테스트 작성.
4. **Green**: v2에서 가장 단순한 구현으로 통과.
5. **Refactor**: 클린코드 원칙 적용. 레이어 경계 준수.
6. **Equivalence**: `tests/equivalence/` 에 동일 입력에 대한 출력 비교 테스트. 개선으로 인한 의도된 차이는 명시적 예외 처리.
7. **Mark v1 Deprecated**: v1 해당 모듈에 `# TODO(v2): replaced by wnw.xxx` 주석 (삭제는 Phase 8).

**복붙 금지 원칙:** 시그니처·SQL 쿼리·프롬프트 템플릿은 참조 가능. 코드 흐름은 다시 씀.

| 기간 폭주 | Phase 단위 체크 | Phase 7 축소 → 체커 일부만 통합, 나머지 차후 릴리즈 |
| v1/v2 DB 스키마 비호환으로 데이터 유실 | 왕복 테스트 | 마이그레이션 스크립트에 dry-run + diff 리포트 |
| 두 폴더 공존 기간 중 혼란 | 코드 리뷰 | CLAUDE.md 상단에 "신규 개발은 v2에만" 명기 |
