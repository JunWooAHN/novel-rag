## 1. 항목별 판정

### 1.1 Anemic Domain Model — ⚠️ **부분 반영**

**비판 요지:** `@dataclass(frozen=True)` + `domain/causality.py`의 순수 함수 분리는 객체를 데이터 가방으로 전락시킬 위험.

**판정 근거:**
- "frozen dataclass + 순수 함수" 조합은 Gary Bernhardt의 *Functional Core / Imperative Shell* 정통 패턴. **Anemic의 정의(=getter/setter만 가진 빈 클래스 + 외부 서비스가 비즈니스 로직 소유)와 다름**. 함수형 코어는 의도된 설계지 누락이 아님.
- 다만 **불변식(invariants) 검증을 객체 자신이 책임지는 부분**은 비판이 옳음. v1처럼 "validate_event(e)"를 호출 측에 맡기면 호출 누락 시 도메인이 깨짐.

**반영 사항:**
- `__post_init__`에서 도메인 불변식 자체 검증을 **의무화** (예: `status=DEAD`이면서 후속 씬에서 caused_by에 자기 자신이 포함되면 즉시 raise).
- 다만 **순수 함수 + frozen dataclass 패턴 자체는 유지**. "도메인 객체에 메서드 많이 박자"는 OO식 권고는 받아들이지 않음.

### 1.2 Primitive Obsession — ✅ **전면 반영**

**비판 요지:** `id: str`, `status: str` 같은 원시 타입은 도메인 의미를 못 담음.

**판정 근거:**
- 비용은 거의 0 (`NewType` 1줄). 이득(타입 체커가 `EventId`와 `CharacterId` 혼동 차단)은 큼.
- v1에서 실제로 ID 혼동 가능성이 있던 곳(`scene_id` ↔ `chapter_id`)을 컴파일 타임에 막을 수 있음.

**반영 사항:**
- 모든 ID는 `NewType`으로 정의: `EventId`, `SceneId`, `ChapterId`, `CharacterId`, `FactionId`.
- 상태/카테고리는 `Enum` 강제 (이미 §1.1.7에 부분적으로 있음 → 명시적으로 격상).

### 2. Result 패턴 (Exceptions as Control Flow) — ⚠️ **선택적 반영 (재시도 루프 한정)**

**비판 요지:** XML 파싱 실패·논리 충돌을 raise → try/except 루프로 처리하면 예외를 GOTO로 쓰는 안티패턴.

**판정 근거:**
- 비판은 정당. 단, **Python 전면 Result 도입은 cargo-cult 위험**:
  - Python에는 native `Result` 타입 없음. `returns` 같은 라이브러리는 학습 비용·디버그 부담 큼.
  - 1인 프로젝트에서 모든 함수 시그니처에 `Result[T, E]`를 다는 건 가독성 손해.
- **합리적 절충:** 자가 교정 루프(Phase 5/6)처럼 **"실패가 비즈니스 흐름의 일부인 곳에서만"** 명시적 결과 타입 사용. 그 외 진짜 예외(IOError, 스키마 손상, DB 잠금)는 raise 유지.

**반영 사항:**
- Phase 5(`xml_validator`), Phase 6(`fact_extractor` SOT 대조), Phase 7(`checkers/base.py`)에서:
  ```python
  ValidationOutcome = Ok[Scene] | Failed(reason: str, suggestion: str)
  ```
  형태의 **discriminated union** 사용. (Python 3.11+ `match` + `dataclass` 조합으로 충분, 외부 라이브러리 무도입.)
- 도메인 layer는 여전히 raise 사용 (`SotConflictError` 등). 이건 "프로그래밍 오류 = 즉시 종료"의 영역.
- **금지선:** "재시도 루프를 try/except의 except 블록에서 돌리기"는 PR 리뷰에서 reject.

### 4. 좁은 Config 주입 (God-Config 회피) — ✅ **전면 반영**

**비판 요지:** 단일 `Config` 객체를 모든 컴포넌트에 주입하면 LLM Client가 DB 경로를 알게 됨.

**판정 근거:** 명백한 옳음. 인터페이스 분리 원칙(ISP)의 직접 적용.

**반영 사항:**
- `config.py`는 단일 god-Config 금지. 다음과 같이 분할:
  - `AnthropicConfig` (api_key, model_name, max_retries)
  - `DbConfig` (path, busy_timeout)
  - `EmbeddingConfig` (model_id, batch_size)
  - `CheckerThresholds` (pacing_min, high_point_density 등)
  - `PipelineConfig` (max_self_correction_loops, max_quality_loops)
- Container는 god-Config를 구성한 뒤 **각 어댑터/서비스에는 좁은 슬라이스만** 주입.

### 5. 횡단 관심사 분리 (Cross-Cutting Concerns) — ✅ **반영, 단 실용선**

**비판 요지:** 로깅·메트릭(`scene_generation.metrics`)이 파이프라인 본문에 박히면 SRP 위배.

**판정 근거:**
- 정당. 하지만 §1.1.3 "순수 도메인" 룰은 이미 도메인을 보호 중이니, **추가로 보호할 영역은 services/pipelines**.
- "철저히 순수" 표현은 과함. 옵저버빌리티는 1차 요구사항.

**반영 사항:**
- 데코레이터/프록시 패턴으로 횡단관심사 분리:
  ```python
  llm = LoggingProxy(MetricsProxy(AnthropicLLMClient(cfg)))
  ```
  으로 Container에서 와이어링.
- pipelines 본문에서 `logger.info()`, `metrics.record()` 직접 호출 **금지** (lint 룰 또는 grep 검증).
- 단, **`raise` 직전 `logger.exception()`** 같은 진단 로깅은 허용 (디버깅 현실).

## 7. 재검토 — AI-Driven Dev 관점에서의 자기 반박 (2차)

**입력:** 사장님 피드백 (2026-04-13 추가)
**핵심 논거:** "1인 사장 + 클로드 코딩 환경에서 '유연함'은 AI가 실수할 여지를 주는 독."

### 7.1 사장님 논거 재요약

1. **보일러플레이트 비용 = 0.** Result 래핑·NewType·match 분기는 인간에게는 고통이지만 클로드에게는 무료. "쓰기 비용이 비싸다"는 내 1차 반론이 잘못된 전제에 서 있었음.
2. **타입 강제 = 환각 억제기.** 타입이 좁을수록 클로드의 출력 분포가 좁아져 버그·논리 비약 확률 급감.
3. **엄격한 아키텍처 = 프롬프트 엔지니어링.** import-linter 룰과 레이어 경계는 클로드에게 "이 모듈은 DB·네트워크를 모름"을 구조적으로 강제 → 엉뚱한 라이브러리 끌어오기 차단.

### 7.2 솔직한 평가 — 사장님이 옳음 (대부분)

**1차 검토에서 내 사고의 결함:**
- **인간 개발자 관점의 비용 함수**로 판단함. "Result 시그니처 매번 쓰는 거 귀찮다"는 명제는 **타이핑 주체가 인간일 때만 성립**. 클로드가 코드를 치는 한, 작성 비용은 사실상 0.
- "Python 관용구" 옹호는 부분적으로 cargo-cult. **관용구는 인간의 가독성을 위한 합의지, AI 협업에서의 정답이 아님.**
- "재시도 루프 위치에만 적용"은 회색지대를 만듦 → 클로드가 PR마다 "이번 함수는 raise? Result?"를 판단해야 함 → 일관성 깨짐의 진입로.

### 7.3 단, 두 가지는 솔직히 반론

사장님 논거가 강력하지만, **순도 100% 강제로 가기 전에 짚어야 할 두 가지**가 있습니다. 무비판 수용은 또 다른 cargo-cult가 될 수 있어서요.

**반론 1: 보일러플레이트 비용은 작성에서 0이지만 *읽기/유지보수*에서는 0이 아님.**
- 클로드도 컨텍스트 윈도우가 유한. Result 래퍼가 5단 중첩되면 Phase 6 디버깅 시 클로드가 한 번에 보는 호출 그래프가 줄어듦.
- 사장님이 PR을 검토할 때 ceremonial 코드가 핵심 로직을 가림.
- **결론:** 강제는 옳다. 단 **"never-fail 순수 함수까지 Result로 감싸지 말 것"** 이라는 닫힌 예외 목록을 미리 박아둬야 함. 안 그러면 클로드가 `Ok(x + 1)` 같은 무의미 래핑을 양산.

**반론 2: 스택 트레이스의 진단 가치를 너무 쉽게 버리지 말 것.**
- I/O 어댑터가 raise → service에서 즉시 Result로 wrap하면, 프로덕션 장애 시 원본 traceback이 잘리거나 chained exception 처리가 누락되기 쉬움 (클로드가 자주 빠뜨리는 패턴).
- **결론:** Result로 감싸도 **원본 예외를 `Failed.cause`에 보존하는 것을 시그니처로 강제**. `Failed(reason: str, suggestion: str)` → `Failed(reason: str, suggestion: str, cause: BaseException | None)` 로 수정.

### 7.4 §1.1.4 강화판 (1차안 폐기, 본안 채택)

```markdown
### 1.1.4 도메인 모델링 절대 룰 (No Compromise)

§1.1.1~7에 더해, AI 주도 개발 환경에서는 아래 4개 룰도 **동급 강제**.
"유연" 또는 "케이스 판단"은 클로드의 환각 진입로이므로 허용하지 않음.

8. **Primitive Obsession 절대 금지**
   모든 도메인 ID는 `NewType`. 상태·카테고리·등급은 `Enum`.
   raw `str`/`int`로 도메인 개념을 표현하면 PR reject.
   - 검증: `mypy --strict` + `domain/`·`services/`에서 raw ID 사용 grep → 0건
   - 닫힌 예외: 외부 경계(파일 경로, HTTP body)는 raw 허용. 경계 안쪽으로 들어오는 즉시 NewType 변환.

9. **Result 패턴 전면 강제 (도메인 + 서비스 전 영역)**
   `domain/`과 `services/`의 모든 비즈니스 연산은 `Result[Ok, Failed]` 반환.
   raise는 **닫힌 예외 목록에서만** 허용:
   - (a) `__post_init__` 불변식 위반 (생성자에서 Result 반환 불가능)
   - (b) I/O 어댑터 내부 (DB/네트워크/파일) — 단 service 진입 직전 Result로 wrap
   - (c) 프로그래밍 오류 (`assert`, `TypeError`) — 정상 흐름이 아님
   `Failed` 타입은 반드시 `cause: BaseException | None` 필드 보유 (스택 트레이스 보존 강제).
   - 검증: `services/`, `domain/`에서 `raise` grep → 위 (a)~(c) 외 0건
   - 검증: try/except 블록 안에서 재시도 루프는 PR reject

10. **횡단 관심사 침투 절대 금지**
    `services/`, `pipelines/`, `domain/`에서 `logger.*`, `metrics.*` 직접 호출 0건.
    실패 진단 정보가 필요하면 `Failed.cause`에 담아 반환 → adapter/proxy 레이어가 로깅.
    - 패턴: `LoggingProxy(MetricsProxy(RealAdapter(cfg)))` Container 와이어링
    - 검증: grep → 0건 (화이트리스트 없음. `logger.exception()` 예외 폐지)
    - 닫힌 예외: `container.py`, `adapters/` 내부만 로깅 허용

11. **God-Config 절대 금지**
    `config.py`는 단일 거대 객체 금지.
    - `AnthropicConfig`, `DbConfig`, `EmbeddingConfig`, `CheckerThresholds`, `PipelineConfig`
    각 컴포넌트는 자신이 필요한 슬라이스 타입만 받음.
    - 검증: 컴포넌트 생성자 시그니처에 `Config` (god) 타입 등장 시 PR reject
```

### 7.7 보류·기각 항목 (2차 갱신)

- **"도메인 객체에 OO식 메서드 풍부 추가"**: 기각 유지. functional core 패턴은 AI 협업에도 유리 (입출력만 보면 됨).
- **"Result 무한 적용 (순수 never-fail 함수까지)"**: 기각. `Ok(x + 1)` 같은 무의미 래핑 금지. **never-fail 함수는 raw 반환** 명시. 단 fail 가능성이 1%라도 있으면 Result.
- **"`logger.exception()` 화이트리스트"**: 1차에서 허용 → 2차에서 **폐지**. `Failed.cause`로 일원화.

### 7.8 솔직한 자기 평가

1차 검토는 **"클린코드 vs 실용주의" 이분법**으로 사고했고, 그 실용주의가 **인간 타이핑 비용**을 전제로 했음. 사장님 피드백은 이 전제 자체가 본 프로젝트에 안 맞는다는 정확한 지적. 2차에서 강제로 회귀하되, **"닫힌 예외 목록"과 "Failed.cause 보존"** 두 가지 안전장치를 추가한 것이 본 검토의 기여. 이 두 가지가 없으면 절대 룰이 도리어 클로드의 ceremonial 코드 양산 + 진단 정보 손실로 이어질 수 있음.
