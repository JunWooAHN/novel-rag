# **자동 집필 RAG 시스템 개발 플랜 및 데이터 명세서**

## **1\. 개요 (Overview)**

본 문서는 하이브리드 RAG 아키텍처 기반의 웹소설 자동 집필 시스템 구현을 위한 실무 개발 플랜, 데이터베이스 스키마 및 핵심 모듈 명세서입니다. 파이썬(Python) 기반의 백엔드 시스템 구축을 전제로 하며, 벡터 기반의 문맥 검색과 절대적 연표(SOT)를 결합한 창작 엔진을 포함합니다.

## **2\. 웹소설 창작 헌법 (Core Genesis Rules)**

LLM의 환각(Hallucination)을 막고 수백 화에 달하는 장편의 개연성을 유지하기 위해 다음의 헌법을 시스템의 최우선 원칙으로 삼습니다.

1. **제1원칙 (Scene-by-Scene):** 소설은 '화(Chapter)' 단위가 아닌 **'씬(Scene)' 단위로 조합하여 완성**한다.  
2. **제2원칙 (SOT \- Source of Truth):** 작품 전체의 뼈대가 되는 \*\*토탈 연표(SOT)\*\*를 구축하며, 모든 인물의 이벤트와 생사 여부, 타임라인은 이 SOT를 기준으로 통제된다.  
3. **제3원칙 (Separation of DB):** SOT(토탈 연표 DB)는 텍스트 본문과 임베딩을 담는 벡터 DB와 **물리적/논리적으로 완전히 분리**하여 관리되는 절대 무결성 핵심 DB다.

## **3\. 데이터베이스 스키마 명세 (SQLite)**

시스템은 '절대 팩트'를 담당하는 SOT DB와 '서사 문맥'을 담당하는 Vector DB, 투 트랙으로 분리되어 운영됩니다.

### **3.1 핵심 SOT DB**

테이블 1: original\_timeline (원 역사 연표 연표)

테이블 2: altered\_timeline(주인공 개입 후 변형된 역사 연표)

인물별 이벤트와 타임라인을 관리하는 관계형 DB입니다. 벡터 검색을 거치지 않고, 프롬프트의 뼈대를 잡기 위해 SQL로 직접 즉시 조회됩니다.

| 컬럼명 | 데이터 타입 | 제약 조건 | 설명 |
| :---- | :---- | :---- | :---- |
| id | INTEGER | PRIMARY KEY | 연표 고유 식별자 |
| date | TEXT | NOT NULL | 작중 날짜 (포맷: YYYY-MM-DD HH:MM) |
| character\_name | TEXT | NOT NULL | 중심 인물명 |
| status | TEXT |  | 인물 상태 (예: 생존, 사망, 부상, 투옥 등) |
| faction | TEXT |  | 소속/세력 |
| major\_event | TEXT | NOT NULL | 해당 일자에 벌어진 인물의 핵심 이벤트 요약 |

### **3.2 vector DB**

테이블: scenes (씬 본문 및 임베딩)

과거의 대화, 묘사, 구체적 서사를 검색하기 위한 벡터 기반 DB입니다. (sqlite-vec 확장 모듈 사용)

| 컬럼명 | 데이터 타입 | 제약 조건 | 설명 |
| :---- | :---- | :---- | :---- |
| id | INTEGER | PRIMARY KEY | 씬 고유 식별자 |
| date | TEXT | NOT NULL | 작중 날짜 |
| characters | TEXT |  | 등장인물 (콤마로 구분) |
| event\_summary | TEXT |  | 씬의 마이크로 요약 |
| content | TEXT | NOT NULL | 씬 본문 전체 텍스트 |
| embedding | FLOATVEC | NOT NULL | 텍스트 임베딩 벡터 |

## **4\. 핵심 모듈 개발 명세 (Core Modules)**

### **4.1. 창작 엔진 (Generation Engine)**

가장 핵심이 되는 웹소설 생성 로직입니다. 씬(Scene)을 하나 생성할 때마다 다음의 루프를 돕니다.

1. **뼈대 조회 (SOT Fetch):** 작성할 날짜와 인물에 해당하는 과거 타임라인을 sot\_chronology에서 SQL로 정확히 가져옵니다. (예: "1592-04-13 기준, 정발은 생존 상태이며 부산진에 있음")  
2. **살점 조회 (Vector Fetch):** 해당 인물의 이전 심리 상태, 대화 톤앤매너 등을 알기 위해 scenes 테이블에서 하이브리드 RAG 검색을 수행합니다.  
3. **프롬프트 융합 & 생성:** SOT(팩트) \+ Vector(문맥) \+ 사용자 지시를 LLM에 주입하여 새로운 씬 본문을 생성합니다.

### **4.2. 텍스트 파싱 및 적재 엔진 (Parser Engine)**

### **4.2. \[모듈 B\] 텍스트 파싱 및 하네스 검증 엔진 (Harness Validation Engine)**

LLM의 출력을 단순 파싱하는 것을 넘어, 데이터의 무결성을 검증하고 구조를 강제하는 '안전벨트' 모듈입니다.

* **하네스 레벨 1: 구조적 강제화 (XML 파싱 \+ Pydantic)** Claude의 특성에 가장 잘 맞는 **XML 태그 출력 방식**을 유지하되, 파싱된 데이터의 무결성을 `pydantic` 라이브러리로 강력하게 검증합니다.  
  * LLM은 지시된 대로 `<sot_update>` 및 `<scene_meta>` 태그 안에 정형화된 데이터를 출력하고, `<scene_content>` 안에 소설 본문을 이스케이프(Escape) 없이 자유롭게 출력합니다.  
  * Python 백엔드는 정규식이나 BeautifulSoup 등으로 XML 블록을 1차 분리한 후, 메타데이터 부분만 `pydantic` 모델에 주입하여 데이터 타입(예: 날짜가 YYYY-MM-DD 규격인지, 필수 인물 데이터가 비어있지 않은지)을 엄격하게 검증합니다.  
* **하네스 레벨 2: SOT 논리 검증 (Logic Gate)** LLM이 생성한 내용이 헌법(SOT)에 위배되지 않는지 검사합니다.  
  * *예시:* LLM이 추출한 `<sot_update>`에 "1592-04-14 정발 생존"이라고 적혀 있으나, SOT DB에 "1592-04-13 정발 사망"으로 기록되어 있다면 \*\*논리적 충돌(Fatal Error)\*\*로 간주하여 데이터베이스 저장을 차단합니다.  
* **하네스 레벨 3: 자가 교정 루프 (Self-Correction Loop)** XML 파싱 실패, Pydantic 타입 에러, 또는 논리 검증 에러가 발생했을 때 파이프라인을 멈추지 않고 스스로 고치게 만듭니다.

### **4.3. 하이브리드 검색 파이프라인 (Retrieval Pipeline)**

Vector DB(scenes)에서 과거 문맥을 추출할 때 사용합니다.

* **1단계: 하드 필터링 \+ 벡터 스캔 (sqlite-vec Query)**  
  SELECT id, date, characters, event\_summary, content  
  FROM scenes   
  WHERE date \< ? AND characters LIKE ?  
  ORDER BY vec\_distance\_cosine(embedding, ?)  
  LIMIT 100;

* **2단계: Cross-Encoder 리랭킹**  
  BGE-M3 (또는 API)를 통해 추출된 100개의 본문과 쿼리 간의 서사적 연관성 재계산 ➔ Top 15 압축.

### **4.4. 프롬프트 엔지니어링 및 캐싱 (Prompt & Caching)**

### **하네스의 안정성을 높이고 비용/속도를 최적화하는 전략입니다.**

**프롬프트 캐싱(Prompt Caching) 적용:** SOT DB(절대 연표) 전체와 시스템 프롬프트(헌법, 태깅 규칙) 등 변하지 않는 거대한 컨텍스트는 **Anthropic의 프롬프트 캐싱 기능**을 활용하여 고정(Pin)시킵니다. ➔ *효과: 매번 SOT를 읽게 해도 API 비용이 90% 감소하며, 응답 지연 시간(Latency)이 극단적으로 줄어듭니다.*

LLM이 구조를 명확히 이해하도록 XML 태그를 적극 활용합니다.

* **유저 프롬프트 조합 예시:**  
  \<absolute\_timeline\>  
  \[SOT DB에서 가져온 인물별 최신 상태 및 최근 3건의 핵심 연표\]  
  \</absolute\_timeline\>

  \<past\_context\>  
  \[Vector DB에서 가져온 관련된 과거 씬 Top 3 요약 및 본문\]  
  \</past\_context\>

  \<instructions\>  
  위의 절대 연표(absolute\_timeline)와 과거 문맥(past\_context)을 엄격하게 준수하여, 다음 사건에 대한 새로운 씬(Scene)을 작성하시오.  
  \- 타겟 일자: 1592-04-14  
  \- 핵심 지시: 정발 장군의 최후와 부산진의 함락을 묘사할 것.  
  \</instructions\>

## **5\. 단계별 개발 마일스톤 (Milestones)**

* **Phase 1 (1주차): 투트랙 DB 아키텍처 및 파서 구축**  
  * SOT DB(sot\_chronology) 및 Vector DB(scenes) 설계/생성  
  * Python 정규표현식 파서 작성 (SOT 업데이트와 Scene 분리 파싱)  
  * 임베딩 API 연동  
* **Phase 2 (2주차): 검색 엔진(RAG) 및 SOT 연동 로직 구현**  
  * SQL 메타 필터 로직 및 sqlite-vec 통합 검색 쿼리 작성  
  * 로컬 BGE-M3 연동  
* **Phase 3 (3주차): 창작 엔진 로직 완성 (LLM 연동)**  
  * SOT/Vector 조회 \> 프롬프트 주입 \> 씬 생성 \> 파싱 \> 투트랙 DB 동시 업데이트의 순환 루프 구축  
* **Phase 4 (4주차): 에러 핸들링 및 안정화**  
  * LLM의 태그 파괴 대응 및 SOT 모순 발생 시 롤백(Rollback) 로직 구현
