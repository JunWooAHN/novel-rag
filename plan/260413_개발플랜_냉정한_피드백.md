# 개발 플랜 냉정한 피드백: 대체역사 웹소설 RAG AI

**대상 문서:** `plan/260413 개발 플랜 및 데이터 명세서.md`
**작성일:** 2026-04-13
**평가 기준:** 대체역사 웹소설이라는 장르 특수성 + 현재 `webnovel-writer/` 기존 자산

---

## 요약 (TL;DR)

> 이 플랜대로 가면 **"사실관계는 안 틀리지만 아무도 안 읽는 소설"을 자동 생성하는 기계**가 나옵니다. 진짜 리스크는 환각이 아니라 **재미**입니다.

플랜은 "팩트 정합성"이라는 한 축만 집중 설계했으나, 웹소설에서 그것은 **필요조건이지 충분조건이 아닙니다.** 또한 이미 존재하는 자산을 전혀 활용하지 않아 중복 개발 리스크가 큽니다.

---

## 🔴 치명적 결함

### 1. 이미 있는 시스템을 재발명하는 중

현재 워킹 디렉토리 `webnovel-writer/scripts/data_modules/`에 이미 다음이 구현되어 있습니다.

| 기존 모듈 | 플랜이 "새로" 설계하려는 것 |
|---|---|
| `index_manager` + `sql_state_manager` | SOT DB 스키마/관리 |
| `entity_linker` | 인물명/별칭 매칭 |
| `context_ranker` + `context_manager` | 하이브리드 RAG 리랭킹 |
| `rag_adapter` | Vector DB 어댑터 |
| `snapshot_manager` | 버전/롤백 관리 |
| `state_validator` | 논리 검증 게이트 |
| `genre_profile_builder` | 장르별 프로파일 |

또한 `skills/`, `agents/` 계층에 이미:
- `pacing-checker` (페이스 검사)
- `high-point-checker` (쾌감 포인트 밀도)
- `reader-pull-checker` (추독력)
- `ooc-checker` (캐릭터 일관성)
- `consistency-checker`, `continuity-checker`

**권고:** 신규 플랜을 실행하기 전 **갭 분석(gap analysis)** 부터 수행. 기존 자산의 절반 이상이 이미 있는 것을 재구현하지 말 것.

### 2. "대체역사"의 본질을 모델링하지 못함

플랜은 `original_timeline` / `altered_timeline` 두 테이블로 분기를 표현하지만, 대체역사의 핵심은 **단일 분기점이 아니라 캐스케이딩 나비효과**입니다.

#### 시나리오
```
정발이 1592-04-13에 죽지 않음
  └─> 부산진 함락 시점 변동
        └─> 동래성 방어 병력 구성 변동
              └─> 신립의 탄금대 배치 결정 변동
                    └─> 선조 파천 시점 변동
                          └─> 의병 봉기 시점 변동
                                └─> ...
```

#### 필요한 것
- **이벤트 DAG (방향성 비순환 그래프)**: `caused_by` FK로 인과 사슬 표현
- **분기 플래그 + 신뢰도**: 각 이벤트가 원사/추측/변형/확정 중 어디인지
- **provenance 추적**: 어느 씬에서 이 SOT 레코드가 유래했는가 (`source_scene_id` FK)
- **롤백 가능 단위**: 10화 수정 시 영향 받는 SOT/Vector 레코드 자동 식별

#### 플랜의 스키마 문제
```
status TEXT    -- "생존" / "사망" / "부상" / "투옥" ... 자유 기술
```
LLM은 "빈사", "중상", "반은 죽은", "숨을 거두기 직전" 등을 쓸 수 있고, SOT 키워드 매칭은 이를 못 잡습니다. **ENUM 혹은 FK 제약 필수.**

---

### 3. 웹소설 장르 지식의 전면 부재

이건 대체역사 **웹소설**입니다. 플랜 어디에도 다음이 없습니다.

| 웹소설 필수 요소 | 플랜의 처리 |
|---|---|
| 사이다/고구마 비율 | ❌ 없음 |
| 훅 밀도 (화당 훅 n개) | ❌ 없음 |
| 떡밥 투척/회수 관리 | ❌ 없음 |
| POV별 독자 인지 상태 (이 정보는 독자가 아직 모름) | ❌ 없음 |
| 화 구성 (씬 → 화 묶음, 클리프행어) | ❌ 없음 |
| 페이싱/긴장도 곡선 | ❌ 없음 |
| 캐릭터 **보이스** 일관성 (팩트와 분리된 말투/가치관) | ❌ 없음 |
| 회귀/빙의물 트로프 (권선징악, 사이다 타이밍) | ❌ 없음 |

기존 `webnovel-writer` 에이전트들이 이미 이 역할을 합니다. 새 플랜은 이걸 버리고 "팩트 검증" 한 축만 세웁니다.

## 🟡 구조적 약점

### 4. 프롬프트 캐싱 90% 절감 주장의 함정

- Anthropic 프롬프트 캐싱은 **캐시된 prefix 부분에만** 90% 할인. SOT가 매 씬마다 업데이트되면 캐시 무효화.
- 200화 넘어가면 SOT 자체가 수만 토큰. "전체 주입"은 파산.
- 해법: SOT를 **append-only 불변 섹션 + 델타 섹션**으로 분리. 인물별/시기별 **뷰 슬라이싱**으로 선택 주입.

### 5. 하이브리드 검색의 순진함

```sql
WHERE date < ? AND characters LIKE ?
```

| 문제 | 영향 |
|---|---|
| `characters LIKE ?` | 별호/관직명/대명사 못 잡음 (이순신/통제사/장군/수군절도사) |
| 엔티티 링킹 전처리 없음 | 기존 `entity_linker.py` 활용해야 함 |
| 쿼리 리라이팅 없음 | 현재 씬 지시문을 그대로 쓰면 semantic drift |
| `date < ?` 하드 필터 | 회상/복선 회수 씬을 못 꺼냄 |

### 6. 자가 교정 루프의 허상

XML 파싱/Pydantic 타입 에러는 잡지만:

> "정발이 이미 죽었는데 다음 씬에서 대사를 친다"

같은 **본문 속 의미적 모순**은 SOT 키워드 매칭으론 못 잡습니다. 본문은 `<scene_content>` 안에 자유롭게 쓰게 했기 때문에, 이를 검증하려면:

```
본문 → 이벤트 추출 (LLM 2차 호출) → SOT 대조 → 충돌 시 재생성
```

이 단계가 **플랜에 누락**되어 있습니다.

### 7. 롤백/재집필 모델 전무

Phase 4에 "롤백"이 한 줄 있지만:

- 40화 쓰다가 10화를 수정하면 **Vector DB의 11~40화 임베딩 중 어느 것이 오염**됐나?
- SOT의 어느 row가 10화에서 유래했나? (**provenance 컬럼 없음**)
- 10화 재집필 후 11~40화 재생성? 수동 반영?

provenance 추적 (`scene_id` FK, `derived_from_event_id` FK)을 **초기 스키마부터** 넣지 않은 건 중대 설계 결함. 나중에 붙이기 매우 어려움.

## 🟢 괜찮은 부분

- **투트랙(팩트/문맥) DB 분리 원칙**: 옳은 판단
- **XML + Pydantic 검증 전략**: Claude에 적합
- **sqlite-vec 선택**: 1인 작가 규모 (~수만 씬)에서 현실적
- **프롬프트 캐싱 활용 아이디어**: 방향은 맞음 (구현 디테일이 순진할 뿐)
- **헌법(Genesis Rules) 명문화**: 좋은 엔지니어링 문화

## 📋 권고안

### 우선순위 1: 기존 자산 감사 (1주일 내)

```bash
webnovel-writer/scripts/data_modules/     # 모듈 단위로 현재 기능 목록화
webnovel-writer/skills/                   # 기존 스킬 역할 파악
webnovel-writer/agents/                   # 기존 에이전트 역할 파악
```

**산출물:** "대체역사용으로 추가/교체할 모듈만" 식별하는 갭 분석 문서.

### 우선순위 2: SOT 스키마 확장

```sql
CREATE TABLE sot_event (
    id INTEGER PRIMARY KEY,
    date TEXT NOT NULL,
    character_id INTEGER REFERENCES character(id),   -- FK로 엔티티 강제
    status_id INTEGER REFERENCES status_enum(id),    -- ENUM
    faction_id INTEGER REFERENCES faction(id),
    event_summary TEXT NOT NULL,

    -- 대체역사 핵심
    branch TEXT CHECK(branch IN ('original','altered','projected')),
    caused_by INTEGER REFERENCES sot_event(id),      -- 인과 DAG
    confidence REAL DEFAULT 1.0,                     -- 추측/확정 구분

    -- provenance
    source_scene_id INTEGER REFERENCES scenes(id),
    created_at TEXT DEFAULT CURRENT_TIMESTAMP
);
```

### 우선순위 3: 검증 축 분리

**두 개의 독립 축을 명시:**

| 축 | 목적 | 담당 |
|---|---|---|
| 팩트 정합성 | 환각/SOT 위반 차단 | 하네스 (신규) |
| 웹소설 품질 | 재미/몰입/훅 | 기존 체커 에이전트 재사용 |

### 우선순위 4: 스코프 축소된 MVP

현 4주 플랜은 비현실적. **MVP 스코프로 축소:**

- **MVP (4주):** 팩트 헌법 준수만 검증되는 10화 생성
- **Phase 5-7 (+4주):** 웹소설 품질 레이어 (훅, 페이싱, 사이다)
- **Phase 8 (+2주):** 롤백/재집필

### 우선순위 5: 본문 팩트 추출 단계 추가

```
[생성 루프]
1. SOT Fetch
2. Vector Fetch
3. LLM 생성 (씬 본문 + <sot_update> 태그)
4. XML/Pydantic 검증  ← 기존 플랜
5. 본문 → 이벤트 추출 (LLM 2차 호출)  ← ★ 신규
6. 추출된 이벤트 vs SOT 대조  ← 기존 플랜의 "레벨 2" 확장
7. 충돌 시 재생성 (max 3회)
```
