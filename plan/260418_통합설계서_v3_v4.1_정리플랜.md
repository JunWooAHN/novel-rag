## 2. v4.1이 v3와 **충돌**하는 지점

### 2.1 HelixDB 인스턴스 구조

- **v3**: 풀 Original HelixDB (모드 1 전용) + 시대별 통합 HelixDB (모드 2 전용). 배타적 가동.
- **v4.1**: 단일 HelixDB. 상시 가동 뉘앙스 ("인메모리 풀 적재 20GB RAM").

**영향**: 모드 배타성·RAM 예산·provenance 규약의 근거가 전부 v3의 이원 구조에 종속됨. v4.1이 맞다면 인덱스 §3.1~§3.5, §4, §7.2, §9 아키텍처 구도 전부 재작성.

### 2.2 분기·변형 관리 모델

- **v3**: `provenance` 2분할 (original_baseline / novel_generated). 원역사·작품역사 공존, 쓰기는 novel_generated만.
- **v4.1**: `timeline_id` 기반 + 레코드 상태 (MODIFIED / CANCELLED). 재귀 CTE로 분기 필터링.

**영향**: 한 작품 내에서 여러 대안 역사를 탐색하려면 v4.1의 timeline_id가 필요. v3 provenance는 1작품=1타임라인 가정. 어느 쪽인가?

### 2.3 하드웨어·토폴로지

- **v3 §1.3**: 물리 서버 GL10, Intel 12코어, RAM 64GB, VRAM 48GB (A40). 단일 서버.
- **v4.1 §1**: MacBook(제어) + A40 48GB 서버(연산) + 원격 스토리지. 분산.

**영향**: A40이 GL10의 일부인가 별개 서버인가? MacBook의 역할이 "사람이 앉는 곳"인가 "Hermes Agent가 도는 별도 노드"인가? 모드 관리 컴포넌트(§8.3 P2)의 배치가 종속.

### 2.4 백업 전략

- **v3**: 언급 없음.
- **v4.1**: 일일 Cron, Supabase 또는 NAS로 rclone 푸시.

**영향**: 역설계 원본 문서가 "Supabase에 SOT 적재"라고 쓴 배경이 여기였을 가능성. Supabase는 **백업 저장소**이지 운영 DB가 아니라는 해석이 성립하면, 역설계 원본의 Supabase 언급은 단순 오기.

### 2.5 전처리 파이프라인

- **v3**: S1~S7 단계 정의 (`original_rdb_schema_v1.md` §2).
- **v4.1 §3.1**: 3단계 축약 (덤프 파싱 → 로컬 태깅 → 분산 적재). "경량 모델"이라고 표현.

**영향**: v3의 Qwen-35B 초벌 판정과 v4.1의 "경량 모델"이 같은 것인지. 경량 모델이 별도 모델이라면 VRAM 예산 영향.

| 항목 | 내용 |

## 4. 정리 방안 (3개 옵션)

### 옵션 A: v4.1을 최신 canonical로 승격, v3는 v4.1에 맞춰 재작성

- 장점: 버전 번호 순리대로
- 단점: v3의 모드 0/0b/1/2/3 분리, 풀/시대별 HelixDB 이원화 같은 성숙한 설계가 상실됨. 역주행.

### 옵션 B: v3 인덱스를 canonical로 유지, v4.1은 "인프라·운영 관점 보조 설계서"로 재정의

- 장점: 성숙도 높은 v3를 유지
- 단점: v4.1의 분산 토폴로지·timeline_id·백업 같은 유효한 추가 개념을 어디에 녹일지 재배치 필요

### 옵션 C: 병합. v3 인덱스 v4로 격상하면서 v4.1의 추가 개념 흡수

- 인덱스 v4 = 지금 v3 인덱스 + Node 1/2/3 토폴로지 + Hermes 구체화 + 백업 + timeline_id 검토
- 충돌 항목(HelixDB 단일/이원, provenance/timeline_id)은 재결정
- `260417 통합 아키텍처 설계서.md`는 legacy로 이동

**권장: 옵션 C.** 두 문서가 같은 날 작성됐고 각자 다른 관점(데이터·모드 vs 인프라·토폴로지)에 강점이 있음. v3의 구조를 유지하면서 v4.1의 추가 개념만 흡수하는 게 손실이 가장 적음.

## 5. 옵션 C를 선택 시 결정이 필요한 항목

아래는 병합하면서 사용자 결정이 필수인 지점들.

### D1. HelixDB 인스턴스 구조

- (a) v3 이원화 유지 (풀 Original + 시대별 통합, 배타적 가동)
- (b) v4.1 단일 상시 HelixDB로 전환
- (c) 혼합: 시대별 HelixDB만 유지, 풀 Original은 필요 시에만 빌드

### D2. 분기 관리 모델

- (a) v3 provenance만 (1작품=1타임라인)
- (b) v4.1 timeline_id (한 작품 내 분기 탐색 가능)
- (c) 둘 다 유지: provenance는 원역사/작품역사, timeline_id는 작품 내 대안 분기

### D3. 토폴로지

- Node 1 (MacBook)의 역할: 단순 UI인가, Hermes Agent 호스팅인가?
- GL10 = A40 서버인가 별개인가?
- 원격 스토리지: Supabase vs NAS 중 택일, 또는 둘 다?

### D4. Hermes Agent 구현체

- v4.1에서 "Tool-use 및 JSON 구조화 출력에 최적화된 에이전트"라고만 기재. 구체적으로:
  - Claude Code? Claude API 직접 호출? 자체 구현?
  - 어느 노드에서 구동? (MacBook / A40 / 둘 다)

### D5. 백업 전략 편입 여부

- 지금 도입 vs 후순위로 미루기

### D6. 전처리 파이프라인 "경량 모델"의 정체

- v4.1 §3.1의 "경량 모델"이 Qwen-35B인지, 별도 모델인지
- 별도라면 VRAM 예산·모드 0 재정의
